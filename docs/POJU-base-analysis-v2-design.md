## 第二部分 · 3 次调用架构（全 high）

```
                    structured(本地已算:日主/旺弱/用神喜忌/格局/神煞/十神/关系/大运流年)
                              │
          ┌───────────────────┴────────────────────┐
          ▼                                          
   【第1次调用 · 真算】 high                          
   输入: structured + "报告需要的算料清单"(见第三部分对齐表)     
   任务: 针对报告每段,逐项真算,输出【结构化结论 JSON】          
        —— 纯命理真词,给机器看,不管好不好读、不打标            
   输出: ReportComputed JSON (每段一个结论条目)               
          │                                          
          ├──────────────────┬──────────────────────┐
          ▼                   ▼                       
  【第2次调用 · 写正文】high  【第3次调用 · 写依据】high      
  输入: 每段 core_conclusion  输入: 每段 core_conclusion     
       (钥匙A·只白话结论)          + bazi_basis(钥匙A+B)      
  任务: 结论扩成白话正文      任务: 照 bazi_basis 真词打标    
       (只管通顺,不碰真词)       出金字+白话解释(照单打,不猜)   
  输出: 每段正文白话          输出: 每段依据块              
          └──────────┬───────────┘
                     ▼
            合并渲染:每段 = 正文 + 折叠依据
                     ▼
                 门禁审计 → 落库 → 展示
```

**为什么这样拆（对应你的判断）：**
- **第1次专心算** → 算得准（不用分心写作）
- **第2次专心写** → 白话通顺（不用分心算、不用分心打标）
- **第3次专心打标** → 金字不漏不错（不用分心组织语言）
- **三次同源**：2、3 次都从第1次的 ReportComputed 长出来 → 正文和依据说的是同一件事,不打架

**全 high**：避开 xhigh 的 openrouter 限制，medium 不够深。三次都 high，成本可控（多几分钱），质量稳。

**串联与容错（时序锁死：1 串行先行 + 2/3 并行）：**
- **第1次是根，串行先行**——必须成功产出 ReportComputed 才进 2/3；坏JSON/空回复→同参数无感重发(上限3-4)。
- **第2、3次并行**——都只依赖第1次结果、彼此不依赖，所以同时发。
  **总时长 = 第1次 + max(第2次, 第3次) ≈ 两次串行的时长，却拿到三次的质量**（拆分最大红利：多一次调用的质量，只花一次调用的额外时间）。
- 任一次失败→同参数重发；重发用尽才提示重试。
- 三次都用异步job(照搬base_analysis已验证机制)——报告大，避免90s墙。

## 第三部分 · ★真算↔报告对齐表（命门 · 锁死"针对性真算"）

> **第1次调用的输出结构 = 报告所有段落的算料清单。报告要什么，就精确算什么。**

`ReportComputed` JSON（第1次调用的输出，逐段对应）—— **每段用"双钥匙"结构**：

> **双钥匙（Dual-Key）设计**：每个段落拆成两把钥匙，锁死"第2次正文"和"第3次依据"围绕同一结论、各取所需、绝不两张皮：
> - **钥匙A `core_conclusion`**（白话结论）：第2次写正文用它，第3次锚结论也用它。
> - **钥匙B `bazi_basis`**（命理真词清单）：第3次打标**专用**——直接给真词，第3次照单打标，**不用猜、不用反推**。

```json
    "value_creation":  { "core_conclusion": "", "bazi_basis": [] },
    "decision_style":  { "core_conclusion": "", "bazi_basis": [] },
    "focus_drain":     { "core_conclusion": "", "bazi_basis": [] }
  },
  "interpersonal": {                      // → 模块三
    "comm_archetype":  { "core_conclusion": "", "bazi_basis": [] },
    "friction_point":  { "core_conclusion": "", "bazi_basis": [] },
    "synergy":         { "core_conclusion": "", "bazi_basis": [] }
  },
  "phase_states": {                       // → 模块四(大运流年真算→状态,零时间锚)
    "baseline":         { "core_conclusion": "", "bazi_basis": [] },
    "rest_phase":       { "core_conclusion": "", "bazi_basis": [] },
    "peak_phase":       { "core_conclusion": "", "bazi_basis": [] },
    "transition_phase": { "core_conclusion": "", "bazi_basis": [] }

  }

```

**为什么双钥匙比"看第2次正文"更安全（朋友的关键洞察）：**
- 第2次正文**已把命理词洗成白话**（食神吐秀→独立钻研能力）。若第3次去看正文反推依据 = **让模型猜"这句白话原本是哪个命理词"→ 打标幻觉/错标**（正是我们一路在治的病）。
- 所以第3次**直接读第1次的 `bazi_basis` 真词**，照单打标，不猜 → 打得准。
- 第2、3次都锚同一个 `core_conclusion` → 绝不出现"正文讲搞技术、依据讲搞管理"的两张皮；各自纯粹（正文只白话、依据只打标）；并行红利不变。

**对齐原则（锁死命门）：**
- **一个报告段落 ↔ ReportComputed 里一个字段 ↔ 第1次真算的一项**。三者一一对应。
- 报告没有的段落 → 不算（不瞎算浪费）；报告有的段落 → 必算（不留空段套话）。
- **溢出结论处理**：若第1次算某段时溢出了有价值的额外结论（报告没预留位置），存进 `refs` 或附加字段 → 第2次渲染时**作为小模块插入**（你说的"加个小模块展示,不浪费算力"）。

### ★第 3 次调用（写依据/打标）专属约束（风控纵深防线）

依据块的合规状态特殊：它**允许且必须**出现命理真词（`⟦t:qi_sha|⟧` 这类打标金字）——这是双层制设计。但正因为"可以写命理词"，模型容易顺手带出不该出现的东西。所以第 3 次 prompt 里额外焊死一条：

> **依据打标约束**：依据块中允许且必须出现命理真词（打标成 `⟦t:slug|⟧`），
> 但**绝不能出现具体公历年份**（如 2026 年）**或疾病断言**（如"易有肺部问题"）。
> 命理真词仅用于**逻辑解释**，解释文案保持**中立、客观**，不带吉凶、不带时间、不带医疗。

**为什么单列**：正文红线（零时间锚/零疾病）在依据块最容易松懈——模型觉得"依据是专业解释，可以详细"。这条和模块四的 `phase_states` 禁时间锚形成**双保险**（两道拦在不同调用里）：就算第1次真算漏了时间锚进结论，第3次写依据时也不会渲染出来。纵深防御。

## 第五部分 · 落地顺序（另起炉灶,验收后切换)

```
lib/base-analysis-v2/
  compute/     第1次真算   {prompt, schema(ReportComputed), call}.ts
  narrative/   第2次正文   {prompt, call}.ts
  evidence/    第3次依据   {prompt, call}.ts
  orchestrate/ 串联+异步job+同参重发+合并渲染
  report-schema.ts  ReportComputed 类型(单一事实源)
```

1. **先定 ReportComputed schema**（第三部分那个 JSON）——它是三次调用的接口,定死。
2. **第1次真算**：prompt(针对性算6模块) + schema + 冒烟(3盘,看结论对不对齐、算料全不全)。
3. **第2次正文**：prompt(拿结论写白话) + 冒烟(看白话通顺、零命理词)。
4. **第3次依据**：prompt(拿结论出金字) + 冒烟(看打标全、无裸词、无简称)。
5. **串联**：orchestrate 接异步job+同参重发+合并双层渲染 + 门禁。
6. **三盘端到端验收**：报告6模块齐全、每段双层、正文白话、依据金字、无时间锚、无金融/医疗/婚恋词。
7. **切换**：v2 稳定 → 前端切到 v2 → 删 v1 链路。

## 已拍板的设计决策（锁定）

1. ✅ **模块四边界**：reasoning 层允许用大运流年真算；`phase_states` 输出层零时间锚（禁 2026年/35岁/丙午年/第几步大运），只输出三态的触发条件+策略。
2. ✅ **一页纸卡片依据**：不给每条 Do/Don't 拆细；卡片底部统一【核心依据折叠块】= 日主格局+核心用神喜神+阶段能量场特征。
3. ✅ **所有图表化内容全部不做**：五行占比图/能量饼图砍掉（本地八字列表已承载）；1.2 能量底色改纯文字。v2 专心做模型文字输出。
4. ✅ **调用时序**：第1次串行先行（根）；第2、3次并行。总时长≈两次串行，拿三次质量。

5. ✅ **全量 6 模块一次做完，不分期**：管线代码（orchestrate/异步job/重发/门禁/渲染）与段落数无关，12段和20段一行不差；`ReportComputed` schema 一次冻结（分期要回来改 schema+重调三次 prompt）；模块四是合规命根（零时间锚防 Chargeback）不能砍。
6. ✅ **双钥匙 schema**：每段 = `core_conclusion`(钥匙A白话结论) + `bazi_basis`(钥匙B命理真词清单)。第2次拿A写正文、第3次拿A+B打标——同源不脱节，第3次照单打标不猜（消除打标幻觉）。

## 与旧机制的关系

- **保留复用**：异步job、同参数重发、SSOT术语表(pojulife-terms)、打标器(第3次用)、门禁审计。
- **不再需要**：v1 那套"一次调用又算又写又打标"的混合提示词(被3次拆分取代)、core_judgments(v2 每段自算,彻底不需要中间层)——**core_judgments 删除的决定,在 v2 里自然实现了**(v2 不依赖它)。
- **删除时机**：v2 跑通切换后,旧 base-analysis 链路 + core_judgments 一起删。
