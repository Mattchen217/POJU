# pojulife — 四产品统一输出规范

> 本文件是 **POJU / Glyph / Match / Syncro 四个产品 + 命主基础分析底座** 的**统一输出标准**。任何改动产品输出、提示词、渲染、合规的工作，都**必须先读本文件并遵循**。目标：四个产品交付给用户的东西，在**术语白话、UI 排版、合规、语气、准确性**上口径一致，且能互为干净的上下文。

最后更新：2026-06（§9 并入《动态关系增补》）

---

## 0. 产品与底座

| 名称 | 角色 | 交付形态 |
|---|---|---|
| **命主基础分析 / 性格画像** | **共用中立底座（数字孪生）** | 中立能量元报告，被四产品作上下文注入 |
| **POJU** | 破局顾问（一事一议，多轮对话 + 行动设计） | 对话 + 主交付（ANALYSIS/CONCLUSION/WHAT TO DO/COMING BACK） |
| **Glyph** | 签象原型反思（一事一镜） | 签象 + 解读 |
| **Match** | 双人合盘（两画像如何相遇） | 关系报告 |
| **Syncro** | 时空方位策略（何时/去何方/做何事） | 矩阵建议 |

**铁律：底座中立，场景化由下游做。** 底座只读「硬件配置」（能量结构），**绝不**定性职业/关系/事件；POJU 问职场、Match 问感情时，由各产品把中立底座投射到各自场景。

## 1. 术语白话 = 金字 + 点击解释（四产品强制）

用户可见正文里的命理术语，一律写成**三段位标记**，由前端渲染成**金色词 + `[···]` + 悬浮/点击白话气泡**。用户**永远看不到裸术语，也看不到生标记**。

### 标记格式
```
⟦t:<id>|<可见软译词>|<该处白话>⟧
```
- `<id>`：**必须用闭集 slug**（见 `lib/glossary/term-closed-set.ts` 的 `CLOSED_SET_SLUG`）。如 `day_master / yong_shen / favorable_element / unfavorable_element / fei_ren / yi_ma / zheng_yin / shi_shen / decade …`。**禁止自造 id**（自造 id 渲染会回退中性金色，丢失极性色）。
- `<可见软译词>`：写给用户看的软翻译（如 `core nature` / `key balancing element`）。`keep_cn` 词（日主/大运/流年/天干地支）拼成 `软译 (干支)`，如 `core nature (丁火)`、`life phase (庚午)`。
- `<该处白话>`：**结合本句语境现写**的 2–4 句人话（比喻 + 现实可做的事 + 对这件事意味着什么）。**同一 id 在不同段落白话必须不同**。白话**只进第 3 段（tooltip）**，不出现在正文。

### 极性三色（靠正确 id）
- 用神/喜神 → `favorable_element` 等 → **绿**
- 忌神/需注意 → `unfavorable_element` 等 → **红**
- 中性命理词 → **金**
极性由 `lib/glossary/term-polarity.ts` 按 id 查。**用错/自造 id = 全部回退中性金色**，是常见 bug。

### 渲染链（勿绕过）
`GlossaryText` / `MarkedInline`（`components/cross-product/GlossaryText.tsx`）解析标记 → `RichReadingText`（`components/cross-product/RichReadingText.tsx`）负责块级排版。**任何展示用户向报告的页面都必须走这条链**——不要用裸 markdown 渲染（否则就是「纯文本、没有金字」的退化，正是要消灭的状态）。

## 2. 闭集准确性（杜绝编造，四产品强制）

模型**只能引用引擎真算出来的命理实例**，禁止凭训练知识补充。

- **神煞闭集 = 9 个**：天乙贵人 / 禄神 / 飞刃(羊刃) / 文昌 / 桃花 / 驿马 / 华盖 / 孤辰 / 寡宿。
- **十神 10 / 十二长生 12 / 干 10 / 支 12 / 五行 5** 见 `term-closed-set.ts`。
- **每次只能用本次 `structured` 实际出现的那几项**（见 `buildStructuredInstanceInventory`）；该清单为空则**整篇不得出现神煞名**。
- **集外禁词**（引擎从不计算，`OUT_OF_SET_FORBIDDEN_HAN`）：空亡 / 元辰 / 阴阳差错 / 六秀日 / 将星 / 劫煞 / 十恶大败 / 学堂 / 国印 / 月德 / 天德 …—— **一律禁止出现**。历史事故：国印/空亡、元辰/六秀日/阴差阳错 均为模型生造，必须拦截。
- **用神/喜神/忌神/强弱/格局**：以 `structured` 为准，只展开解释，**不得改判或另算**。

### 落库门禁（强制）
用户向报告**落库/交付前**必须跑 `auditDeliveredText`：**命中集外神煞、断标记（`⟦` 与 `⟧` 不配对）、裸干支 任一 → 拒绝落库并重生成**。这是共用底座的硬门禁（因为它喂全产品）。`auditOutOfSetTerms` 不能只 `console.warn`，要能阻断。

## 3. 降维 UI 排版（奢侈品交付，四产品强制）

排版要像 **Apple 官网 / 顶级杂志**：精炼、克制、留白；**禁止「## 标题 + 一堵字墙」**。渲染器 `parseReadingBlocks`（`lib/reading/parse-reading-blocks.ts`）已支持以下语法，模型**必须输出**：

| 要素 | 语法 | 渲染 |
|---|---|---|
| 子标题 | `### 标题` | h3 |
| 粗体引导块 | `**真实要旨短语:** 正文` | lead 块（粗体标签 + 正文） |
| 金句框 | `> **核心句:** …` | pullquote |
| 列表 | 每条独占一行 `- item` | `<ul>` |
| 短段 | 空行分段 | p |

**硬规则：**
- 每段 ≤ 80 词（中文 ≤ 120 字），**一个论点一段**。
- 每个 `##` 分区至少 1 个粗体引导句；含行动的分区至少 1 个金句框或 bullets。
- **粗体标签必须是真实要旨短语**（如 `**冷却缺口:**`），**禁止字面输出 `Bold lead:` / `Lead:` 占位符**（历史 bug）。
- **bullets 每条独占一行**，禁止把多个 `- ` 挤在同一段（否则不渲染成列表）。
- **金色词密度：每段 ≤ 2 个**，只在该论点首次关键诊断处标；逐柱类段落尤其收敛。

## 4. 命主底座 = 中立四维（数字孪生）

底座是**中立精密读数 + 人话注解**，不是人生故事。四个维度（绑定 `structured`）：

1. **核心底色（强项）** — 驱动力类型 + 能量在何种机制下产生最大价值（十神组合现代转译）。绑 `day_master / strength`。
2. **系统脆弱点（需注意）** — 不谈吉凶，只谈配置短板（缺冷却→冲动、结构过载→内耗）。绑 `ji_shen / 缺失五行`。
3. **能量平衡锚（解决方案）** — 中立非场景调谐（作息/环境心理学/决策习惯）。绑 `yong_shen / xi_shen + 调候`。
4. **高杠杆发力区（全力以赴方向）** — 何种系统状态下最易突破（不预测事件、不指定行业）。绑 `yong_shen` 得力状态。

**硬禁（防污染下游）：**
- ✗ 编造具体职业/行业/经营状态/雇佣/婚育/资产/具体人际（「你开咖啡馆」「雇个帮工」）。改条件式倾向：「你适合直接面对人、靠亲和力做事的工作」。
- ✗ 预测未来事件（新合伙/扩张/某年发生 X）。只给能量倾向。
- ✗ 医疗与脏腑点名（心/肝、忌酒忌辣）。健康改为中立「系统过载/内耗」+ 作息环境类。
- ✗ 逐柱罗列原始数据（藏干/十神/神煞枚举）——那是 `structured` 的职责，叙事复述既冗余又是幻觉重灾区。

## 5. 合规红线（全产品）

- 不算命、不预测具体未来事件/日期、不下吉凶命定、不替用户做决定。
- 不制造恐惧（凶煞不得渲染成「无端损失/灾祸」）。
- 不给医疗/财务/法律诊断建议。
- 时机只用「能量节律 / life phase / 能量气候」，**禁公历年/干支纪年作时间锚**。
- 禁 astrology / divination / psychic / horoscope 字样；POJU/Glyph/Match/Syncro 自有术语体系。
- 详见 `lib/llm/compliance/output-policy.ts` 与 `compliance-terms.ts`（audit-only，不改写，靠模型生成时写对 + 落库门禁拦截）。

## 6. 语气 + 语言

- **语气**：plainspeak（短句、直接、有温度、不软糯）；**全文一个主比喻**，比喻服务于解释能量机制，不刷屏、不编现实情节。
- **语言跟随用户**：回复语言跟随**用户消息语言**（`getPojuChatLanguageDirective`），不是 UI locale。
- **⚠ 语言漂移事故**：曾出现英文提问、模型用德语回复（DeepSeek V4 Pro 经 **GMICloud** 节点）。语言漂移多为**供应商/节点**问题。处置：① `OPENROUTER_PROVIDER_ORDER` 按序钉供应商（如 `DeepSeek,Baidu,Alibaba`）；② `OPENROUTER_PROVIDER_IGNORE` 禁用漂移供应商（如 GMICloud）；③ 提示词语言指令保持强约束。

## 7. 下游上下文隔离（底座如何被消费）

`formatBaseAnalysisForPrompt`（`base-analysis-context.ts`）给下游注入两样：
- **`structured` JSON = 事实源**（完整、确定性，下游据此推理）。
- **叙事 `display_text`（去标记后）= 语气/框架参考**，**不作事实**。

**铁律：下游准确性靠 `structured`，不靠叙事长度。** 叙事要中立、准确、保住四维综合即可，不必为「详细」塞回逐柱原始数据。注入处应标注：「以下为中立能量底座，供场景投射；勿反推具体职业/关系/事件」。

## 9. 动态关系 / 流年 / 十神张力（四产品增补 · 已并入）

> 原《四产品统一规范·动态关系增补》全文已并入本节。共享引擎：`lib/calculations/relation-engine.ts` → 统一 `RelationLabel`。

### 9.1 新数据是什么（四产品共用同一套本地计算）
确定性算出、以统一 `RelationLabel` 输出：
- **本命关系**（相冲/相刑/相害/六合/半合/三合/天干五合）— 盘级、恒定；
- **流年引动**（流年×命局的冲刑合）— 随年变；
- **十神张力**（伤官见官/枭神夺食等）— 本地十神逻辑。

**一次计算，四产品共用。** 不许各产品各写一套关系判定。

### 9.2 各产品怎么用（场景不同，数据同源）
| 产品 | 主要吃哪部分 | 用来干嘛 |
|---|---|---|
| **POJU** | 本命 + 流年引动，**按 question_category 定向过滤** | 破局：结构性原因锚在真实关系上 |
| **Syncro** | **流年引动为主** | 何时/去何方/做何事 |
| **Match** | 双盘 + **今年双人动态** | 两画像相遇 + 流年张力 |
| **Glyph** | 本命 + 流年取当下质地 | 签象为何在此刻呈现这种拉扯 |

### 9.3 闭集纪律（和神煞同一套 · 命门）
1. **进实例清单**：`buildStructuredInstanceInventory` + 下游「流年/定向」段 — 模型**只能引用算出的关系**。
2. **进守卫**：`buildChatFactGuardBlock` 覆盖神煞 + 本命关系 + 流年/定向。
3. **进落库门禁**：`auditDeliveredText` 拦截集外关系词 → 拒绝落库/重生成。

### 9.4 软翻译 + 中性化
- 关系词三段位金字 `⟦t:<id>|软译|该处白话⟧`；冲/刑/害→红，合/半合/三合→绿，天干合→金。
- **中性化，禁凶断**：伤官见官→「外部约束下的对抗张力」；相冲→「两股力的正面顶撞」；相刑→「彼此消耗的拉扯」。**禁**凶/灾/克死/破败/血光。

### 9.5 算全 ≠ 写全（内容 + 风格 · 与 §3 降维联动）
- 每个产品只挑**与本场景最相关的 1–3 条**关系织进叙事，其余是判断底料、**不写给用户**。
- 每类事实（神煞/关系/十神/大运）最多点 1–2 处，且必须落到「**意味着什么 + 第一步/何时/何方**」。
- 全文关系相关金字 **≤3**；降维不变：一个论点一段、每段金字 ≤2、全文一个主比喻。**数据越多，越要克制**。
- 代码侧提示词：`POJU_OUTPUT_DATA_DISCIPLINE`（`poju-base.ts`）→ v6 user 控制面 + 主交付整合要求。

### 9.6 前缀缓存（工程）
- **本命关系**（恒定）→ 随 base_analysis 进数据面（v6 仍在 user 侧实例清单，不进 system）；
- **流年/定向**（每轮/每年可能变）→ **user 侧** downstream（collecting/delivery）。
- 验收：`test-poju-v6-prefix-cache-stability.ts` — system SHA256 字节恒定。

### 9.7 动态关系自检（在 §8 清单基础上追加）
- [ ] 关系是否**只用了 relation-engine 算出的**（没让模型自己推刑冲合害）？
- [ ] 关系词是否三段位金字、slug 来自引擎、极性对？
- [ ] 是否**中性化**（无凶/灾/克死），伤官见官等已包装成系统张力？
- [ ] 是否**只写了 1–3 条相关关系**、没有逐关系罗列？关系金字 ≤3？
- [ ] 本命/流年分区是否正确（缓存没退化）？
- [ ] 落库门禁是否覆盖集外关系词？
