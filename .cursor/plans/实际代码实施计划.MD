实际代码实施计划
我建议分成六个实施阶段。不是六次重新设计，而是同一套 v1.2 SoT 的分阶段落地。
Phase 1 · DC 核心数据层
第一阶段

新建 lib/poju/decision-context/：
- types.ts
- fact-combination.ts
- opening-seed.ts
- hypothesis-from-core.ts
- dir-from-agenda.ts
- dir-aggregator.ts
- conflict-lifecycle.ts
- stop-criteria.ts
- content-hash.ts
- freeze.ts
- versioning.ts
- persist.ts
同时修改 lib/poju/types.ts，增加 decision_context 和 decision_context_versions[]。

验收： Fact 状态组合、user_confirmed 派生、DIR 多 Fact 聚合、Conflict 生命周期、Hash 和版本规则全部通过独立单元测试。

Phase 2 · 持久化与一致性

修改：
- lib/poju/session-manager.ts
- lib/poju/cycle-db-sync.ts
- components/poju/POJUChatUI.tsx
实现 C1：快照、工作副本、提交、失败回滚、幂等和 restore 权威保护。

验收： 模拟 DC 写失败、控制面同步失败、IndexedDB 保存失败、重复请求和页面恢复，均不能产生半完成决策状态。

Phase 3 · Opening + Call A/B

修改：
- lib/poju/agent.ts
- lib/poju/agent-state.ts
- lib/poju/phases/opening/control.ts
- lib/poju/phases/segment2/control.ts
- app/api/poju/breakthrough-core/route.ts
- app/api/poju/breakthrough-core/agenda/route.ts
数据流改造：
- Opening 临时字段通过 opening-seed 进入 DC Definition、初始 Facts 和 Constraints。
- Call A 返回的 breakthrough_core 经 hypothesis-from-core 转换为 DC Hypothesis。
- Call B 的 Agenda 经 dir-from-agenda 转换为 DC DIR。
- Call A/B 服务端输入从 DC 提供正式决策依据，不再把 agent_v2 当作权威决策数据源。
- Call B 仍可保留 Agenda 流程状态，但不得将其状态当成 DIR 状态。
验收： Opening、Call A、Call B 的正式决策数据均能在 DC 中追溯来源；agent_v2 恢复不能覆盖 DC。

Phase 4 · Collecting + 统一停问

修改：
- lib/poju/agent.ts
- lib/poju/state-machine.ts
- lib/poju/agent-state.ts
- lib/poju/investigation-agenda.ts
- lib/poju/collecting-confirmation-gate.ts
- lib/poju/collection-progress.ts
- lib/llm/phases/collecting-phase-v6.ts
- lib/llm/phases/collecting-phase.ts
实现：
- 用户回答 → RealityFact / Conflict 写入 DC。
- 每轮重新计算 DIR。
- Agenda covered 只表示流程进度。
- 所有旧停问入口统一委托 stop-criteria.ts。
- PUSH_GATE 不再产生独立实质追问。
- stall / MAX_COLLECTING_TURNS 与决策充分性分离。
- V5 回退路径也必须遵循 DC Gate。
验收： 所有旧 Gate 的调用入口都不能绕过 DC sufficiency。

Phase 5 · Freeze + V1/V2

修改或接入：
- freeze.ts
- versioning.ts
- Stage3 transition 所在的 agent.ts / state-machine.ts
- confirmation-* 相关入口
实现：
- Stage3 决策充分性结束时 Freeze。
- open Conflict 转为 unresolved_in_final。
- final Context 只读。
- 用户后续补充创建 V2，不修改 V1。
- Stage4 只预留 context_id + version + hash 绑定，不实现 Stage4 管线。
验收： Freeze 不依赖购买或报告 CTA；报告前后不能出现版本错配；Stage4 不能写回 DC。

Phase 6 · 集成测试与验收
最终阶段

使用现有测试基础：
- test-opening-identity-only-dataplane.ts
- test-face-agenda-stage2.ts
- test-agenda-spine-coverage.ts
- test-collecting-covered-reask.ts
- test-collecting-wrapup-summary-gate.ts
- test-opening-duplicate-response.ts
新增 DC 专项测试，重点覆盖：
- Fact 状态组合及非法组合拒绝。
- DIR 多 Fact 聚合。
- Conflict Freeze。
- C1 回滚和幂等。
- DC restore 权威。
- V1→V2。
- 未知信息可能改变 P5 排序时不得误判充分。
- V5/V6 两条路径的 Gate 一致性。
最后执行类型检查、相关测试和构建验证，并按已锁定的八维价值标准进行盲测。
