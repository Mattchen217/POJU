## 2.4 Job 创建和恢复的正式要求

远程 Job 必须支持以稳定的 `client_task_id` 识别原始创建请求。

正式身份：

`session_id + generation_type + client_task_id`

Job 创建必须具备幂等语义：

- 第一次请求：创建 Job 并持久化创建身份。
- 相同身份重复请求：返回原 Job。
- 不得为同一创建身份创建第二个 Job。
- 不得因为 HTTP 响应丢失就假定 Job 创建失败。
- 不得因为 KV 索引尚未写入就盲目创建新 Job。

建议使用持久化 Job metadata 和 KV 索引：

`poju-xhigh:client_task:{phase}:{session_id}:{client_task_id} -> job_id`

提供对应查询能力：

`getXhighJobByClientTaskId(...)`

索引不是唯一身份来源。Job 记录必须保存可验证的创建身份。

如果 Job 创建与 KV 索引不能在同一个原子存储操作中完成，必须明确：

- Job 记录是权威身份记录。
- KV 索引如何重建。
- 重复请求如何查回原 Job。
- 索引缺失时如何恢复。
- 并发创建如何保证唯一。

Reload 恢复顺序：

1. 读取原 Session GenerationTaskContext。
2. 保留原 `client_task_id`、generation 身份、base revision 和 fingerprint。
3. 根据 client_task_id 查询原 Job。
4. 找到原 Job，验证身份后补绑。
5. 查询结果存在歧义，进入 `recovery_required`。
6. 不得创建新 generation 身份。
7. 不得无条件创建第二个 Job。

**S0 验收门槛：** 两份清单和 Job 恢复能力结论必须完整。S0 未验收不得进入 S1。

# 3. S1 — Session CAS Foundation

目标：建立全仓唯一 Session blob 写入机制，为 Generation 提交提供可靠的并发和持久化基础。

主要文件：

- `lib/db/poju-db.ts`
- `lib/poju/types.ts`
- `lib/poju/session-manager.ts`
- 新增 `lib/poju/session-mutation.ts`
- 相关 Session 写入调用者

## 3.1 双 Revision

正式字段：

- `session_revision`
- `dc_write_revision`

职责：

| 字段 | 递增条件 |
|---|---|
| `session_revision` | 每次成功写入 Session encrypted blob |
| `dc_write_revision` | 只有正式 DC 内容发生实质变化时 |

两者都必须在 Session blob 和对应 DB row 中持久化，并保持镜像一致。

初始化：

- 双方均无 Revision：只允许通过明确的 CAS 初始化操作建立初始值。
- 双方初始化成功后保持一致。
- 并发初始化只能有一个成功。
- 失败方重新读取最新记录。
- 只有一方存在 Revision：硬失败。
- 双方 Revision 不一致：硬失败。
- Revision 类型非法：硬失败。
- 普通读取不得静默修复或初始化 Revision。

Revision 不一致错误：

`REVISION_MIRROR_MISMATCH`

禁止通过普通 save 覆盖错误 Revision。

## 3.2 统一 CAS 写入

实现统一核心：

`casWritePOJUSession(...)`

要求：

1. 在事务外读取、解密和准备候选内容。
2. 在事务外完成加密。
3. 进入 Dexie transaction。
4. 重新读取最新 row。
5. 比较 expected `session_revision`。
6. 检查 Revision 镜像。
7. 满足条件才写入候选 encrypted blob。
8. 同时更新 row/blob Revision。
9. 事务失败时不得留下部分提交。

Revision 规则：

- 每次 blob 写入，`session_revision + 1`。
- 只有 DC 实质变化，`dc_write_revision + 1`。
- 非 DC 写入不改变 `dc_write_revision`。
- Path C 只更新 Session 状态时，DC Revision 不变。

禁止在 Dexie transaction 中执行长时间 Web Crypto 操作。

## 3.3 Mutation API

新增：

`mutatePOJUSession(operation_id, mutation)`

要求：

- `operation_id` 稳定。
- Mutation 必须是纯函数或具备等价的可重复执行保证。
- 不允许把旧 Session working copy 整包覆盖最新 Session。
- CAS 冲突后重新读取最新 Session。
- 在最新 Session 上重放原始 Mutation。
- 重试继续使用原 `operation_id`。
- 不得因重试生成新操作身份。

消息去重：

- 相同 `client_id` + 相同消息内容：幂等。
- 相同 `client_id` + 不同消息内容：硬失败。
- 不同 `client_id`：保留两条消息。
- Reload、重试、跨 Tab 均必须遵守相同规则。

## 3.4 所有写入入口收敛

S0 盘点的全部生产 blob 写入入口必须接入统一 CAS。

具体要求：

- `createPOJUSession()`：create-if-absent，禁止覆盖已有 Session。
- `savePOJUSessionCore()`：改为统一 CAS。
- `extendPOJUV4Session()`：区分元数据更新与 blob 更新，避免并发续期导致旧 Session 覆盖。
- `commitDecisionContextChange()`：使用统一 CAS。
- `savePOJUSession()` 及其他封装：不得形成第二套写入实现。
- 其他所有间接写入路径：必须接入统一入口。

禁止业务层直接对 `pojuSessionRecords.encrypted_data` 执行 put/update。

S1 完成后，提交全量写入入口审计报告，逐项证明不存在绕过路径。

## 4.3 Operation Binding

每个 idempotency_key 必须有明确的持久化 Binding。

Binding 必须能证明：

- 该 key 属于哪个 Session。
- 属于哪个 Generation。
- 属于哪个 client_task_id。
- 对应哪个 base_revision。
- 对应哪个 fingerprint/version。
- 对应哪个 Job。
- 当前提交状态是什么。

Binding 与 Registry 的身份不一致，必须硬失败。

不能只依靠 `completedKeys` 内存 Set 判断 Generation 已完成。

## 4.4 GenerationTaskContext

正式持久化于：

`POJUSessionState.generation_task_contexts[]`

字段至少包括：

- client_task_id
- session_id
- generation_type
- generation_id
- base_revision
- job_id
- sync_task_id
- fingerprint
- fingerprint_version
- status
- created_at
- updated_at
- 其他 Final Contract 明确规定的任务状态字段

状态机采用 Final Contract 已定义状态，不自行新增或合并状态。

Task 创建：

1. 读取当前 Session S0 和 DC Revision D0。
2. 创建稳定 client_task_id。
3. 生成 Normalized 输入及 fingerprint。
4. 使用 CAS 保存 `pending_create`。
5. 创建远程 Job。
6. 通过 CAS 将 job_id 绑定到原 TaskContext。
7. 任务执行和轮询使用同一身份。

如果 Job 创建成功但本地绑定失败：

- 进入可恢复状态。
- Reload 保留原身份和 base。
- 通过 client_task_id 查回原 Job。
- 找到原 Job 后补绑。
- 不得无条件创建新 Job。

Reload 不得重新生成一个不同的 Generation 身份来替代原任务。

## 4.5 Path A / B / C

### Path A：首次正式提交

前置条件：

- Registry 中不存在该 Generation 的 completed 记录。
- Generation 身份完整。
- Fingerprint 与版本一致。
- 当前 DC Revision 等于原始 generation_base_revision。

提交时：

- 使用最新 Session Revision 作为 CAS expected。
- 使用原始 generation_base_revision 校验 DC。
- Session 和 DC 的并发更新规则必须遵守 Final Contract。
- 同一 C1 内写入正式 DC、ControlPlane、Registry、Binding、TaskContext、幂等记录和 Revision。
- `session_revision + 1`。
- `dc_write_revision + 1`。

如果当前 DC 已经变化：

`GENERATION_BASE_STALE`

禁止把旧 Generation 结果合并到新 DC。

### Path B：相同 key 的重放

必须识别已完成的原始提交。

返回：

`GenerationReplayResult`

包含：

- 原始提交凭据。
- 原 generation_id。
- 原 fingerprint/version。
- 原 base_revision。
- 原 result_marker。
- 当前 Session/DC Revision。
- `original_result_is_current`。

规则：

- 不再次写入 DC。
- 不递增 Revision。
- 不重复执行原提交副作用。
- 不重新生成结果。
- 不能把历史结果无条件标记为当前结果。

### Path C：相同 Generation、不同新 key

前置条件：

- Generation 身份完全一致。
- Registry 中已有相同 Generation 的完成记录。
- 新 key 不存在冲突。
- 不存在身份碰撞。

操作：

- 新增 Operation Binding。
- 新增对应幂等 stamp。
- 不写入 DC。
- `session_revision + 1`。
- `dc_write_revision` 不变。

连续不同 key 重试：

- 不重复写 DC。
- 不产生重复 Registry。
- 不改变 Generation 身份。
- 每个 key 的 Binding 均可恢复和审计。

## 4.6 generation_guarded

Phase 2 `idempotent_first` 必须保留原有行为。

Generation 使用独立 `generation_guarded` 路径。

必须处理：

- `beginPersistTransaction()` 的 key-only early return。
- `commitPersistTransaction()` 内部的 key-only early return。

不能只修改其中一处。

Generation 的处理顺序：

1. 验证 Session 和 Generation 身份。
2. 检查历史 Registry。
3. 检查身份 Collision。
4. 检查 Operation Binding。
5. 判断 Path A/B/C。
6. 执行对应 C1 操作。

任何 collision 不得因为 key 已完成而被静默跳过。

- Constraint 必须独立执行合法组合校验。
- Gate 确认不得批量确认 Facts 或 Constraints。

删除旧的：

`user_confirmed_event?: boolean`

不得保留 boolean 作为正式确认事实来源。

## 5.3 Opening Anchor

新增：

`opening-anchor.ts`

Opening Anchor 必须有专用身份，不能直接使用普通消息 client_id 代替。

至少绑定：

- anchor_id
- session_id
- 对应的 assistant message client_id
- message role
- 状态
- 创建时间
- 清除时间（适用时）

规则：

- Understanding 卡片创建与首次 Anchor 持久化处于同一 C1。
- 普通 assistant message 不自动成为 Anchor。
- 普通 client_id 不等于 anchor_id。
- Reset 必须在同一 C1 中完成旧 Anchor 清除记录和新 Anchor 创建。
- History append-only。
- Reload 能恢复当前有效 Anchor。
- Gate 确认不创建 Fact Confirmation Event。

# 6. S4 — Normalization / Fingerprint / Mapper

目标：保证 Fingerprint 和正式业务映射使用同一份规范化输入。

主要文件：

- 新增 `normalize-*`
- `fingerprint.ts`
- `opening-seed.ts`
- `hypothesis-from-core.ts`
- `dir-from-agenda.ts`

## 6.1 唯一 Normalized Object

强制处理顺序：

`Validate → Normalize → Normalized Object → Fingerprint + Mapper`

Fingerprint 和 Mapper 必须消费同一个 Normalized Object。

禁止：

- Fingerprint 使用一套标准化逻辑。
- Mapper 使用另一套标准化逻辑。
- Fingerprint 计算后再对输入进行额外过滤。
- Mapper 自行重排数组或改变字段值。
- 通过两个相似但独立的对象声称语义一致。

## 6.2 Normalization 规则

按照 Final Contract 实现：

| 输入类型 | 规则 |
|---|---|
| Unicode | NFC |
| 换行 | CRLF / CR 统一为 LF |
| 字符串 | trim，连续空白折叠 |
| 空字符串 | 规范化为 null |
| 空白字符串 | 规范化为 null |
| undefined/null | 按契约统一规则处理 |
| 非法类型 | FAIL |
| 对象 | 对象键稳定排序 |
| 数组 | 保留顺序 |
| 数组下标 | 保留原始下标 |
| 数组空槽 | 按契约保留，不得过滤后重新编号 |
| 数值 | 使用确定性的规范化和序列化规则 |
| Fingerprint | 纳入 fingerprint_version |

Fingerprint 必须基于规范化后的 canonical JSON 和版本信息计算 SHA-256。

Fingerprint 版本变化必须产生不同的指纹身份。

## 6.3 Call A 字段映射

`hypothesis-from-core.ts` 必须消费 Normalized Object。

逐项覆盖 Final Contract 指定字段：

- `situation_conclusion`
- `energy_structure`
- `key_crossroads.real_fork`
- `key_crossroads.path_costs`
- `key_crossroads.decision_traits`
- `key_crossroads.needs_validation`
- `key_crossroads.structural_basis`
- `modern_action_frames[i].direction`
- `modern_action_frames[i].why_fits`
- `modern_action_frames[i].needs_validation`
- `modern_action_frames[i].structural_basis`
- `modern_action_frames[i].chart_anchors`
- `primary_path.direction`
- `primary_path.why_fits`
- `primary_path.needs_validation`
- `primary_path.structural_basis`
- `backup_path.direction`
- `backup_path.why_fits`
- `backup_path.needs_validation`
- `backup_path.structural_basis`
- `energy_retune_frame.direction_fit`
- `energy_retune_frame.timing_ripeness`
- `energy_retune_frame.daily_retune`
- `energy_retune_frame.needs_validation`
- `energy_retune_frame.structural_basis`

规则：

- Call A 只创建 Hypotheses。
- 不得创建 Facts 或 Constraints。
- Hypothesis 稳定 ID 必须遵守 Final Contract。
- Fingerprint 与 Hypothesis mapper 使用同一 Normalized Object。
- `modern_action_frames` 保留原始数组索引。

## 6.4 Call B 字段映射

`dir-from-agenda.ts` 必须消费 Normalized Object。

字段：

- id
- label
- collection_goal
- role
- frame_kind
- supports
- serves_page
- critical

规则：

- 一个 AgendaItem 对应一个 DIR。
- `dir_id = dir_${agendaItem.id}`。
- 不允许自动合并 AgendaItem。
- 不允许自动拆分 AgendaItem。
- 重复 Agenda ID 必须 HARD FAIL。
- Agenda 顺序保持不变。
- DIR 初始状态为 unknown。
- Agenda covered 不等于 DIR known。
- Agenda status 不得直接决定 DIR state。

## 6.5 Opening Seed

`opening-seed.ts`：

- 只写 Definition、初始 Facts、初始 Constraints。
- 只使用用户提供的陈述作为用户事实来源。
- 不得将模型推断写成用户确认事实。
- 不创建正式 Hypotheses。
- 不创建 DIR 或 Agenda。
- Fact/Constraint 必须经过合法状态组合校验。
- Confirmation Event 按 S3 契约处理。
