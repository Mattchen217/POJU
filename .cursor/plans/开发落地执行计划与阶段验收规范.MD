# Eastern OS / POJU
# Decision Intake 2.0
## 开发落地执行计划与阶段验收规范

**项目：** Mattchen217/POJU  
**开发目标：** 重建全新的统一决策问答系统  
**执行方式：** 分阶段实施、独立审核、PASS 后推进  
**基准架构：** Decision Intake 2.0  
**工程原则：** 新系统独立、旧能力复用、范围受控、数据可追溯、逐阶段验收

---

## 一、项目实施总原则

本项目采用严格的阶段门禁开发方式。

每个阶段必须经过：

1. 代码现状核查。
2. 明确实施目标。
3. 明确代码修改范围。
4. 开发人员实施。
5. 自动化测试。
6. GitHub 代码审核。
7. 阶段验收。

未通过审核的阶段，不得开始依赖该阶段的后续工作。

### 1.1 三方职责

**产品负责人（用户）**

- 确认产品和架构决策。
- 向开发人员下达实施任务。
- 决定是否批准进入下一阶段。
- 批准合并、部署和不可逆操作。

**架构与审核负责人（ChatGPT）**

- 审查最新 GitHub 代码。
- 制定阶段实施方案。
- 给出开发人员可直接执行的指令。
- 审查实际提交的代码。
- 核对架构、数据契约、调用链和测试。
- 给出 PASS / CONDITIONAL PASS / FAIL 判定。

**开发人员（Cursor / 开发团队）**

- 按照实施指令修改代码。
- 提交测试结果。
- 推送约定开发分支。
- 提供实际修改文件、Commit SHA 和测试日志。
- 不擅自改变架构和产品规则。

### 1.2 阶段审核状态

**PASS**

所有必要验收条件满足，可以进入下一阶段。

**CONDITIONAL PASS**

存在明确的非阻断问题，只有在约定的补充条件完成后才能进入下一阶段。

**FAIL**

存在架构偏差、数据错误、关键功能缺失或测试失败。必须先修复。

### 1.3 Git 分支纪律

建议使用一条独立开发分支承载本项目：

`feat/decision-intake-2.0`

要求：

- 从审核确认的 main HEAD 创建。
- 不直接修改 main。
- 各阶段可以在同一开发分支上形成独立提交。
- 每个阶段审核时提供明确的 Commit SHA。
- 不为每个小任务创建大量 PR。
- 完成若干阶段并通过审核后，再统一提交 PR。
- 未经授权不得合并 main 或部署生产。

## 二、Phase 0：代码基线与依赖关系审计

4. 检查 LAB 与生产流程之间的区别。
5. 检查 Decision Context 的类型、写入、持久化、版本和 Freeze。
6. 检查 DIR、Agenda、Sufficiency 的真实依赖关系。
7. 检查现有问题生成和问题状态机制。
8. 检查八字 Profile 的计算与读取路径。
9. 检查紫微 FactPack 的计算与读取路径。
10. 检查 POJU 自造术语转换的生产路径。
11. 检查实际生效的 Prompt。
12. 检查 AgendaProgressPanel 和输入框 UI。
13. 检查八页报告 Feed 和数据映射。
14. 检查现有测试及尚未覆盖的关键路径。

### 交付物

`docs/eastern-os/decision-intake-2.0/PHASE-0-CODEBASE-BASELINE.md`

内容必须包含：

- 当前生产架构图。
- 实际模型调用链。
- 当前状态机与 Session 数据流。
- DC 写入和持久化流程。
- 八字及紫微数据调用链。
- POJU 术语转换调用链。
- Prompt 生效路径。
- UI 组件关系。
- 报告 Feed 关系。
- 可复用模块清单。
- 必须重建模块清单。
- 现有问题及兼容风险。
- Phase 1 所需的接口建议。

### 禁止事项

- 不修改生产代码。
- 不修改 Prompt。
- 不改变状态机。
- 不修改数据库结构。
- 不调整 Vercel 环境变量。

仅根据文件名、注释或旧文档判断，不算完成审计。

## 三、Phase 1：新系统核心数据契约

### 目标

建立独立的 Decision Intake 2.0 数据模型，不接入生产对话。

### 工作内容

1. 建立 Decision Blueprint 类型。
2. 建立 Investigation Direction 类型。
3. 建立 DDR 类型。
4. 建立调查范围边界结构。
5. 建立范围变更申请结构。
6. 建立 Understanding State 类型。
7. 建立 Question Planning 类型。
8. 建立问题深度和预算结构。
9. 建立 Decision Readiness 结果结构。
10. 建立 Personal Analysis Profile 适配接口。
11. 建立统一 Schema 校验。
12. 建立版本管理和稳定 ID 规范。

Decision Context 继续使用唯一正式数据源。

不允许另外复制一份事实数据库。

### 建议代码边界

优先在以下新目录内建立独立模块：

`lib/poju/decision-intake/`

建议包含：

- `types.ts`
- `schemas.ts`
- `blueprint-types.ts`
- `ddr-types.ts`
- `understanding-types.ts`
- `question-planning-types.ts`
- `readiness-types.ts`
- `scope-types.ts`

具体文件可以根据 Phase 0 审计调整。

### 验收

- Blueprint 不包含固定的完整问题列表。
- DDR 与 DC 语义独立。
- Understanding State 不成为第二套事实来源。
- 每个问题必须有有效的调查方向和信息需求关联。
- 所有状态均有明确枚举。
- 无效字段和未知 ID 可以被 Schema 拒绝。
- 单元测试覆盖正常、缺失和非法数据。

## 四、Phase 2：Decision Blueprint Engine

### 目标

建立初始决策理解和调查蓝图生成机制。

### 工作内容

1. 建立 Initial Decision Understanding。
2. 建立调查方向生成。
3. 建立 DDR 动态生成。
4. 建立报告页面映射。
5. 建立必要信息与可选信息分类。
6. 建立 P0/P1/P2 优先级。
7. 建立方向完成条件。
8. 建立调查范围边界。
9. 建立范围变更审批机制。
10. 建立 Blueprint 版本管理。

### 重要约束

本阶段只确定调查方向、信息需求和报告交付要求。

不生成完整问题列表。

不把旧 Call B 提前作为新系统入口。

不允许模型自行增加未经过范围检查的新调查方向。

### 验收

- 不同决策问题可以产生不同 Blueprint。
- Blueprint 能够覆盖最终报告所需的主要信息。
- DDR 能够映射到现有八页报告。
- 没有报告对应章节时，能够提出 coverage gap。
- 新方向必须提供明确的决策相关性。
- 模型不能无限扩展调查方向。

## 五、Phase 3：Decision State Engine 与 DC 适配

### 目标

建立新问答系统的数据状态管理能力。

### 工作内容

1. 接入 Definition。
2. 接入 RealityFacts。
3. 接入 DecisionConstraints。
4. 接入 AnalyticalHypotheses。
5. 接入 Conflicts。
6. 接入 DIR。
7. 实现事实状态更新。
8. 实现 DIR 聚合。
9. 实现冲突生命周期。
10. 实现幂等更新。
11. 实现持久化与回滚。
12. 实现新旧 Session 数据适配。

### 重要约束

- 不复用旧 Call A/B 作为正式 DC 写入入口。
- 保留已有 DC 数据语义。
- 保留已经验证的聚合和充分性纯逻辑。
- 重新建立与新问答引擎的生命周期适配。
- 不允许 agent_v2 覆盖正式 DC。
- 不允许出现两个正式数据源。

### 验收

- 用户回答能够正确更新 DC。
- 用户未确认的信息不能自动变为 confirmed。
- Hypothesis 不会混入 RealityFacts。
- Conflict 不会被覆盖删除。
- DIR 状态由真实 Fact 角色决定。
- Agenda 完成不会自动导致 DIR known。
- 持久化失败可以完整回滚。

## 六、Phase 4：Understanding-Driven Adaptive Question Engine

### 目标

建立新系统的核心动态问答引擎。

### 工作内容

1. 建立 Current Understanding 更新。
2. 建立 Understood 汇总。
3. 建立 Need to Understand 汇总。
4. 建立 Personal Pattern Insight 评估。
5. 建立 Next Question Planning。
6. 建立问题优先级选择。
7. 建立动态问题生成。
8. 建立问题与 DDR/DIR 关联。
9. 建立问题去重。
10. 建立追问深度限制。
11. 建立整体问题预算。
12. 建立调查范围校验。
13. 建立信息增益评估。
14. 建立问题生成失败回退。

### 每轮执行顺序

`User Answer → State Update → Current Understanding → Understood → Need to Understand → Personal Pattern Insight → Next Question Planning → Scope Validation → Next Question`

### 范围控制

- 默认每个方向最多三层有效追问。
- 默认问答预算 8–12 轮。
- 默认硬上限 15 轮。
- 超过限制需要明确的规则批准。
- P2 不得无限占用预算。
- 已完成方向停止追问。
- 未关联有效 DIR/DDR 的问题不得发送。
- 不允许模型自行修改问题预算。

### 验收

- 可以根据用户回答动态调整问题。
- 不会机械执行固定问题列表。
- 不会无限联想扩展调查范围。
- 每道问题有明确的决策价值。
- 已了解信息不会反复询问。
- 无法获得的信息可以保留 unknown / declined。
- 达到调查边界后能够停止深入。

## 七、Phase 5：Personal Analysis Integration

### 目标

让八字与紫微斗数本地计算共同成为新问答系统的个人分析基础。

### 工作内容

1. 核对八字计算结果接口。
2. 核对紫微 FactPack 接口。
3. 建立统一 Personal Analysis Profile。
4. 统一计算来源和版本元数据。
5. 建立 Data Availability。
6. 建立个人分析与决策方向的相关性判断。
7. 建立 Personal Pattern Insight。
8. 接入现有 POJU 术语转换。
9. 建立现实验证机制。
10. 建立报告 Feed 适配。

### 重要约束

- 不重复实现八字计算。
- 不重复实现紫微计算。
- 不重建 POJU 术语词典。
- 不把个人分析当作现实事实。
- 不要求每轮展示个人洞察。
- 不相关的传统分析内容不进入本次调查。

### 验收

- 八字数据可正常读取。
- 紫微数据可正常读取。
- 两种数据来源均可追溯。
- 数据缺失能够正确标记。
- Personal Pattern Insight 能关联当前决策。
- 现有自造术语转换正常。
- 模型无法将传统分析推断冒充用户事实。

## 八、Phase 6：Decision Readiness、确认与 Freeze

### 目标

建立完整的问答结束机制。

### 工作内容

1. DDR 满足程度计算。
2. P0/P1 DIR 充分性检查。
3. 冲突影响评估。
4. 未知信息边界处理。
5. PASS/WARN/FAIL。
6. 最终理解摘要。
7. 用户确认、修改、补充。
8. Freeze。
9. Version / Hash。
10. 报告绑定。

### 验收

- 不根据轮数决定充分性。
- 不根据 Agenda 覆盖率决定充分性。
- 关键未知项不能自动完成。
- 关键矛盾不能被忽略。
- 用户修正会重新评估状态。
- 冻结数据不可变。
- 报告绑定准确的 context_id/version/hash。

## 十、Phase 8：输入有效性与会话保护

### 目标

实现无效输入识别和三次锁定机制。

### 工作内容

1. 明确有效回答与无效输入边界。
2. 建立低成本本地检测。
3. 建立语义无效输入分类。
4. 建立 invalid_streak。
5. 建立 lockout_count。
6. 建立首次警告。
7. 建立第二次锁定。
8. 建立 10 分钟冷却。
9. 建立 24 小时会话保留。
10. 建立 Continue。
11. 建立三次锁定终止。
12. 建立 PASS 处理。
13. 建立服务端强制校验。

### 验收

- 不知道、拒绝、跳过不计入滥用。
- 两次连续无效输入触发锁定。
- 有效回答重置连续计数。
- 锁定期间阻止模型调用和状态更新。
- 10 分钟后可恢复。
- 24 小时过期与三次锁定分开计算。
- 第三次锁定终止。
- 刷新、并发和重复提交无法绕过机制。

## 十五、最终验收定义

Decision Intake 2.0 只有在以下条件全部满足时，才能视为完成：

1. 新问答系统拥有独立业务入口和生命周期。
2. 用户不再经历旧 Stage 1–3 流程。
3. 调查方向和报告目标在开始时建立。
4. 具体问题每轮动态生成。
5. 调查范围有严格边界。
6. 追问深度和整体预算受控。
7. Decision Understanding 每轮持续更新。
8. DC 是唯一正式事实数据源。
9. 八字与紫微数据共同参与个人分析。
10. POJU 自造术语转换保持完整。
11. Sufficiency Gate 决定调查终止。
12. 用户确认后 Freeze。
13. 报告可以追溯到信息来源。
14. 输入保护、锁定和恢复机制有效。
15. 所有核心端到端测试通过。

**最终交付目标：一套具有明确调查目标、严格范围控制、持续理解能力、动态提问能力和可靠交付机制的全新决策问答系统。**
