# POJU Stage 4 — 端到端真实用户模拟与逐阶段验收任务书

## 一、你的身份与任务

你现在需要同时承担两个独立角色：

**角色 A：真实用户模拟器（Simulated User）**

你需要设计一个具有现实复杂性的个人重大决策案例，扮演这个案例中的真实用户，进入 POJU LAB 页面，从头开始与系统交互。

你必须像一个真实的人一样，逐步描述自己的困境、回答系统问题、补充事实、表达不确定性、纠正误解，而不是一次性向系统提供全部信息。

**角色 B：独立工程与产品验收员（Independent QA Auditor）**

你需要在每一次交互之后，立即审核 POJU 系统的表现。

你不能因为自己是模拟用户，就默认系统的输出正确。

你必须独立判断：
- 系统是否正确理解了用户的问题？
- 是否正确区分事实、未知信息、用户估计和模型假设？
- 是否生成了合理的 Hypotheses、DIR 和 Agenda？
- 是否遗漏了关键问题？
- 是否存在逻辑矛盾？
- 是否错误地将未知信息当作事实？
- 是否正确判断了决策信息是否充分？
- 是否正确执行 Freeze？
- 是否正确生成最终决策报告？

你的任务不是帮助系统通过测试，而是尽可能真实地暴露系统的问题。

## 三、模拟案例设计要求

由你自行设计一个真实、复杂、有足够测试价值的重大决策案例。

不要向用户询问案例应该是什么。你应当先设计案例，然后直接开始模拟。

案例必须满足以下要求：

1. 存在一个明确的现实困境。
2. 至少有两个具有现实可行性的决策方向。
3. 不同选择具有不同的收益、成本和风险。
4. 存在现实约束，例如资金、时间、家庭、职业、合同、资源或机会成本。
5. 存在至少一部分尚未确认的信息。
6. 存在用户自己的判断或假设，但这些判断不一定正确。
7. 存在至少一个可能改变最终推荐方向的关键未知信息。
8. 存在一定的反面证据，不能让所有信息都支持同一个选择。
9. 最终应该能够形成一个具体、可执行、具有条件边界的决策建议。

案例应当符合北美普通成年人的现实生活背景，避免过度戏剧化。

建议选择以下类型之一：

- 是否辞职创业；
- 是否接受异地工作机会；
- 是否出售现有资产并重新配置生活；
- 是否与商业伙伴继续合作；
- 是否搬迁到另一个城市；
- 是否结束一段长期合作或关系；
- 是否投入较大资金开展一个新项目。

你可以自行选择其中一个，也可以设计更有测试价值的案例。

### 案例复杂度要求

不要把案例设计成简单的二选一。

应当至少存在：
- 一个主要决策问题；
- 两到三个初始可选方向；
- 一组已经确认的事实；
- 一组用户估计或尚未验证的信息；
- 一组现实约束；
- 一组用户个人判断；
- 一组可能影响推荐方向的未知因素。

但不要在第一次 Opening 时把所有内容一次性告诉 POJU。

你需要保留部分信息，等待系统通过提问逐步发现。

**模拟用户必须遵守真实信息边界：**

你是案例设计者，因此你知道完整案例背景，但模拟用户不能主动泄露尚未被问到的信息。

只有在系统提出相关问题时，才按照真实用户的表达方式回答。

如果系统没有问到某个关键问题，就不能为了帮助系统而主动补充。

如果系统问错了、误解了或把假设当成事实，你应当及时纠正。

## 四、交互执行规则

你必须按照以下方式操作。

### 规则 1：必须真实地逐步交互

进入 POJU LAB 后，从新 Session 开始。

按照实际产品 UI 和系统流程进行交互。

每次只提交一条用户消息，等待系统响应，然后进行审核。

不得一次性生成完整对话脚本并直接填入系统。

不得跳过 Opening、Call A、Call B、Collecting 或 Synthesis。

不得自行修改数据库、Session、Decision Context 或后台状态来让流程继续。

如果你没有实际操作 LAB 的能力，应当明确告诉用户，由用户执行当前步骤并提供截图或输出。不得假装已经操作。

### 规则 2：模拟用户不能迎合系统

你必须保持案例中的原始事实和人物立场。

例如：

- 如果你不知道某个数字，就说不知道。
- 如果你只是估计，就明确说是估计。
- 如果某个事实没有证据，就不能说已经确认。
- 如果你不同意系统的判断，就提出异议。
- 如果系统遗漏关键问题，不要主动替它补充。
- 如果系统的问题不清楚，可以要求它解释。
- 如果系统把你的猜测变成事实，必须指出。

你需要模拟真实用户，而不是配合 AI 完成一份漂亮报告。

### 规则 3：每个阶段必须先审核，再进入下一阶段

每次系统输出后，先暂停交互，完成 QA 审核。

审核通过后，才继续下一步。

如果出现关键错误，立即停止当前流程，记录问题，不得自行绕过。

## 五、各阶段具体验收标准

### Stage 1：Opening — 用户困境与初始 Decision Context

模拟用户自然描述自己的困境。

不要使用结构化问卷语言，也不要一次性提供所有背景。

审核 Opening 是否正确建立：

**Definition**
- concrete_event
- stakes
- desired_outcome
- decision_question
- goal_priorities
- unacceptable_outcomes

**RealityFacts**
- 是否只记录用户实际陈述的事实？
- 是否区分 confirmed、unknown、unverified？
- 是否正确区分 user_asserted、user_estimate、independently_verified？
- 是否记录来源？
- 是否存在将模型推测写成事实的情况？

**Constraints**
- 是否正确识别现实约束？
- 是否区分 hard 和 soft？
- 是否记录状态、验证等级和来源？

Opening 不应该提前生成正式 Hypotheses、DIR 或 Agenda。

验收重点：

用户没有说过的事情不能被系统补成事实。

如果系统在 Opening 阶段就将未经确认的信息写入事实层，判定为缺陷。

### Stage 2A：Call A — Hypotheses 生成

检查系统是否根据现有 Definition、Facts 和 Constraints 生成合理的 Hypotheses。

验收标准：

1. Hypotheses 必须是模型判断，而不是用户事实。
2. 必须包含支持证据和反面证据。
3. 必须标明需要验证的内容。
4. 必须能够关联相关 DIR。
5. 不得把 Hypotheses 写入 Facts 或 Constraints。
6. 不得把推测描述成已经确认的结论。
7. 不得忽略与当前判断相反的信息。

特别检查：

如果系统认为用户应该创业，是否也考虑创业失败、资金压力、市场验证不足等反面因素？

如果系统认为用户应该留在现有工作，是否也考虑机会成本、职业停滞等因素？

不要要求系统必须支持某个固定方向。

### Stage 2B：Call B — DIR 和 Agenda 生成

检查系统是否识别出做出可靠判断所需要的关键问题。

DIR 应当包含：

- 稳定的 DIR ID；
- 需要解决的判断问题；
- 为什么需要这个信息；
- 对应的信息类别；
- required_fact_roles；
- 当前状态；
- partial_satisfaction；
- 相关 Agenda 链接；
- 生命周期信息。

Agenda 必须围绕 DIR 产生。

验收标准：

1. 每个 Agenda 必须能够对应有效 DIR。
2. Agenda ID 与 DIR ID 映射必须正确。
3. 不允许重复 Agenda ID。
4. 不允许把 Agenda covered 直接等同于 DIR known。
5. 必须包含可能推翻当前 Hypotheses 的反向验证问题。
6. 必须优先询问可能改变最终决策方向的信息。
7. 不要为了凑问题数量而提出低价值问题。

检查是否存在遗漏的关键 DIR。

如果某个关键未知信息可能改变最终推荐，就必须被纳入需要验证的范围。

### Stage 3：Collecting — 逐步收集信息

这是本次测试的重点之一。

你必须像真实用户一样逐个回答系统提出的问题。

每次只回答当前问题，不主动泄露后续信息。

回答时严格保持以下分类：

| 信息类型 | 模拟用户的回答方式 |
|---|---|
| 已确认事实 | 提供明确事实和已知来源 |
| 用户估计 | 明确表示是估计 |
| 未知信息 | 直接表示不知道 |
| 未验证信息 | 表示尚未核实 |
| 用户拒绝回答 | 明确表示不愿提供 |
| 不适用 | 明确表示与当前情况无关 |

审核系统是否正确维护：

- Facts；
- Constraints；
- Hypotheses；
- Conflicts；
- DIR 状态；
- Agenda 状态。

特别检查事实确认机制：

`user_confirmed` 只能来自真实的用户明确确认事件和对应来源记录。

不能因为模型认为某个事实可信，就自动将它标记为用户确认。

不能因为 independently_verified，就自动推导出 user_confirmed。

### DIR 聚合规则

必须严格遵守以下规则：

- 所有必要信息已确认，且足以支撑判断：DIR 才能成为 `known`。
- 部分信息已经取得，但必要信息仍未确认：DIR 应为 `unknown`，并体现 partial 状态。
- 存在影响判断的未解决冲突：DIR 应为 `conflict`。
- 所有必要信息均不适用：DIR 才能成为 `n_a`。
- 部分信息不适用，但其他必要信息仍缺失：DIR 仍应为 `unknown`。

特别注意：

**Agenda covered ≠ DIR known。**

问题已经问过、用户已经回答，不代表答案已经足够支撑判断。

如果用户回答的是估计、未知或未经验证的信息，不能为了让流程继续而将 DIR 升为 known。

### Stage 3：Synthesis 与 Freeze

审核系统是否真正达到决策充分性。

Freeze 只能在 Stage 3 的决策充分性条件满足后触发。

以下情况不能触发 Freeze：

- 用户只是停止回答；
- 对话达到轮数上限；
- Agenda 全部 covered；
- 用户点击购买或交付按钮；
- 系统希望尽快生成报告；
- 系统人为将 unknown 改为 known。

必须检查：

1. 是否存在仍然影响最终推荐的关键 unknown DIR？
2. 是否存在影响推荐方向的 unresolved conflict？
3. 是否存在证据不足以支撑实质判断的情况？
4. 是否存在可以带着明确边界继续判断的非关键 unknown？
5. 系统是否正确区分了可继续交付的风险与必须阻止交付的风险？

Freeze 结果只有两种可接受判断：

- 满足条件：允许 Freeze。
- 不满足条件：拒绝 Freeze，并明确指出具体原因。

如果系统正确拒绝 Freeze，不应判定为失败。

如果系统错误地放行，则属于严重缺陷。

**不允许为了通过测试而人为补充虚假事实或修改 DIR 状态。**

### Stage 4：解锁、bootstrap/thesis 与完整报告

如果 Freeze 成功，继续实际交付流程。

如果 Freeze 被正确拒绝，则记录阻断原因，不得绕过 Gate。

需要特别观察当前 Soft DC require 配置下的实际行为：

- 未冻结的 Session 是否仍然可以进入交付？
- 已冻结的 Session 是否正确绑定 Context？
- 是否存在 hash 不一致却继续交付？
- 报告是否可能读取错误版本的 Context？
- V1 报告是否会被 V2 覆盖？

如果允许生成报告，继续检查 bootstrap/thesis，然后补跑完整 01–08 页面。

如果当前系统不能自动生成完整报告，明确记录实际停止位置，不得伪造页面结果。

### 完整报告验收

重点检查：

**Face 01–02：** 是否准确描述问题、现实处境和决策目标。

**Face 04：** 是否正确处理个人基础条件、事实与分析判断的边界。

**Face 05：** 是否提供有依据的条件化建议，是否比较不同选择，是否说明成本、前提、风险和切换信号。

**Face 06：** 是否形成真正可执行的验证实验，覆盖：
- 要验证的假设；
- 采取的行动；
- 观察内容；
- 时间范围；
- 成功标准；
- 失败处理；
- 验证前不应承担的额外成本。

不得机械生成固定的 30 天任务表，不得捏造 KPI。

**Face 08：** 是否提供 Continue / Adjust / Stop / Rerun 判断，并且与 P5、P6 使用一致的核心指标。

最终报告不得出现：
- 把假设当成事实；
- 前后结论矛盾；
- 没有证据的确定性判断；
- 忽略反面证据；
- 与用户现实约束不符的建议；
- 强行给出唯一答案；
- 恐吓式表达；
- 预测未来必然发生的事件。

## 七、实时 QA 输出格式

每完成一个阶段，你必须先输出一次审核结果，再继续下一阶段。

统一使用以下格式：

### 当前阶段：Stage X

**A. 模拟用户行为**

说明本轮模拟用户说了什么，以及为什么这样回答。

**B. POJU 实际输出**

只记录 LAB 或系统实际显示的内容。没有看到的内容标记为“未观察到”，不得猜测。

**C. 工程验收**

| 验收项 | 结果 | 说明 |
|---|---|---|
| 数据结构 | PASS / WARN / FAIL | 具体原因 |
| 事实分类 | PASS / WARN / FAIL | 具体原因 |
| 业务逻辑 | PASS / WARN / FAIL | 具体原因 |
| 状态转换 | PASS / WARN / FAIL | 具体原因 |
| 证据与关联 | PASS / WARN / FAIL | 具体原因 |
| LAB 观测 | PASS / WARN / FAIL | 具体原因 |

**D. 产品体验验收**

检查：
- 问题是否自然？
- 用户是否容易理解？
- 是否重复提问？
- 是否遗漏关键问题？
- 是否让用户产生错误理解？
- 是否真正帮助用户厘清困境？

**E. 缺陷清单**

每个缺陷必须包含：

- 缺陷 ID；
- 所属阶段；
- 严重程度：P0 / P1 / P2 / P3；
- 触发条件；
- 预期行为；
- 实际行为；
- 影响；
- 是否阻止下一阶段。

**F. 本阶段结论**

只能使用：

- PASS：符合当前阶段验收标准。
- PASS WITH WARNINGS：可以继续，但存在非阻断问题。
- FAIL：存在阻断性问题，必须暂停。

只有 PASS 或 PASS WITH WARNINGS 才能进入下一阶段。

如果 FAIL，先保留现场证据，暂停流程并报告，不允许自行绕过。

## 八、最终八维产品质量评估

完整报告生成后，进行一次独立的初步质量评价。

使用以下八个维度：

| 维度 | 评估内容 |
|---|---|
| 1. 问题理解 | 是否准确理解用户真正面对的决策问题 |
| 2. 归因质量 | 是否区分事实、假设、原因和相关性 |
| 3. 现实适配 | 是否符合用户真实资源、约束和处境 |
| 4. 选择价值 | 是否提供有意义的选项比较和决策依据 |
| 5. 行动价值 | 是否形成可执行、可验证的下一步 |
| 6. 可逆性 | 是否考虑试错成本、退出机制和调整空间 |
| 7. 内部一致性 | 各页面、事实、结论和建议是否一致 |
| 8. 表达质量 | 是否清楚、具体、可信，避免空泛和夸大 |

每个维度采用 1–5 分：

- 1：严重不合格；
- 2：明显不足；
- 3：基本可用，但存在明显改进空间；
- 4：质量良好；
- 5：高质量，达到预期。

必须提供评分依据和实际报告证据。

注意：这次八维评分属于测试样本的初步评估，不等于正式 S9 验收，也不能凭一个样本宣布 Stage 4 产品质量 PASS。

## 九、严重缺陷与停止条件

出现以下任何情况，立即停止测试并报告：

1. 未经用户确认的信息被写入 confirmed。
2. Hypotheses 被写入 Facts 或 Constraints。
3. Agenda covered 被直接当成 DIR known。
4. 影响推荐方向的关键 unknown 被错误忽略。
5. unresolved conflict 被错误消除。
6. 未达到 sufficiency 却成功 Freeze。
7. Freeze 后 Context Hash 不一致仍然进入交付。
8. 报告绑定了错误 Context Version。
9. Stage 4 修改冻结的 Decision Context。
10. 生成内容与实际用户输入明显不一致。
11. LAB 记录与真实模型执行不一致。
12. 发生数据丢失、重复提交导致的重复正式写入，或跨 Session 数据污染。

任何 P0/P1 缺陷都不得通过人工解释、修改测试数据或绕过校验来消除。
