# 第一部分：项目目标与架构重建原则

## 1.1 项目背景

现有系统采用分阶段式决策咨询流程，内部存在 Stage 1、Stage 2、Stage 3，以及对应的 Call A、Call B 等模型调用。

这些流程原本承担不同阶段的任务，例如初步问题理解、深度分析、生成调查问题以及持续收集用户信息。

经过重新讨论，确定现有阶段式流程已经不符合产品未来的交互方向。

新系统不再要求用户依次进入不同阶段，而是从用户提出决策困境的第一条消息开始，持续进行理解、分析、提问、信息收集和状态更新。

用户只会感受到一个连续的、个性化的决策理解过程。

因此，本次工作不是升级旧的 Stage 1–3，也不是简单调整 Call A 或 Call B，而是：

**重新设计并建立一套独立的、完整的统一决策问答系统。**

旧系统中的部分成熟代码和能力可以经过审查后复用，但新系统必须拥有独立的业务架构、状态机、问答调度机制和生命周期。

## 1.2 新系统的核心目标

新系统需要解决六个问题：

1. 从用户最初提出的问题开始，持续理解用户真正面临的决策困境。
2. 在开始时建立明确的调查范围和目标，知道最终报告需要回答哪些问题。
3. 根据用户的实际回答，动态调整问题顺序、问题内容和调查优先级。
4. 始终围绕已经确定的调查方向，不允许模型无限联想、无限扩展问题。
5. 持续整合现实信息、个人分析、决策约束和模型判断。
6. 当信息达到报告所需的充分性后，进行最终理解确认，冻结决策上下文，并生成正式报告。

新系统的核心定位：

**目标固定，范围受控，问题动态，状态持续更新，结果可验证。**

## 1.3 必须遵守的架构原则

### 原则 A：新系统独立建设

不再以旧 Stage 1、Stage 2、Stage 3 作为业务流程基础。

不将 Call A、Call B 提前或改造成新问答系统的核心入口。

新系统需要建立自己的：

- Decision Blueprint
- Decision Context
- Decision State Engine
- Adaptive Question Engine
- Decision Readiness Engine
- Decision Intake Orchestrator
- Decision Intake UI
- Session Lifecycle

旧代码只作为经过审查的底层能力库使用。

### 原则 B：目标和调查范围先于问题

系统开始时必须明确：

- 用户正在面对什么决策。
- 本次决策最终需要得出什么结论。
- 为得出结论必须调查哪些方向。
- 每个方向需要掌握什么信息。
- 哪些信息属于必要条件，哪些属于辅助信息。
- 哪些方向不属于本次决策范围。

系统不应该在开始时生成一份固定的几十道问题清单。

它应该先建立调查蓝图，再根据用户的回答逐步生成具体问题。

### 原则 C：动态提问，但不能无限扩展

动态提问不代表自由联想。

模型只能在预先确定的调查范围内调整问题。

允许：

- 调整调查方向的优先级。
- 深入追问已经确定方向中的关键未知信息。
- 根据用户回答发现该方向下新的必要信息。
- 识别影响决策判断的矛盾。
- 跳过已经充分了解的内容。
- 在确有必要时提出范围内的补充问题。

不允许：

- 无限制地引入新的调查主题。
- 因为一个回答联想到多个与决策无关的问题。
- 为了追求信息完整而不断扩展调查范围。
- 重复询问已经确认的信息。
- 把普通兴趣、背景知识和无关细节变成新的调查任务。
- 因为模型认为某个话题有趣，就增加新的追问。

**任何新调查方向都必须能够说明它与当前决策目标之间的直接关系。**

如果无法说明它如何影响最终选项、风险判断、推荐结论或执行前提，则不得加入本次调查。

# 第二部分：新系统总体架构

## 2.1 总体工作流程

新系统采用一个连续问答流程，不向用户展示阶段编号。

内部架构如下：

```text
用户提出决策困境
        |
        v
初始决策理解
        |
        v
建立 Decision Blueprint
        |
        +-----------------------------+
        |                             |
        v                             v
确定调查方向                  确定报告交付要求
        |                             |
        +--------------+--------------+
                       |
                       v
             初始化 Decision Context
                       |
                       v
             Decision Intake Orchestrator
                       |
                       v
               Decision State Engine
                       |
                       v
              识别当前信息缺口
                       |
                       v
              调查范围与优先级检查
                       |
                       v
              Adaptive Question Engine
                       |
                       v
                生成下一道问题
                       |
                       v
                  用户回答
                       |
                       v
                输入有效性检查
                       |
                       v
                更新 Decision Context
                       |
                       v
               重新计算信息状态
                       |
                       +------> 继续动态问答
                       |
                       v
               Decision Readiness Engine
                       |
              是否满足充分性条件？
                       |
             +---------+---------+
             |                   |
             否                  是
             |                   |
             v                   v
         继续调查          最终理解摘要
                                 |
                                 v
                           用户确认/修正
                                 |
                                 v
                            Final Freeze
                                 |
                                 v
                            正式报告生成
```

以上是系统内部工作流程，不代表用户需要按照这些步骤分别操作。

## 2.2 四个核心引擎

### 1. Decision Blueprint Engine

负责建立本次决策的调查蓝图。

它确定本次决策的：

- 决策目标。
- 调查范围。
- 调查方向。
- 必要信息。
- 报告交付要求。
- 信息之间的依赖关系。
- 不属于本次调查的内容。

它是新系统的目标约束层。

### 2. Decision State Engine

负责管理所有已经收集的信息及其状态。

包括：

- 用户明确表达的信息。
- 已确认的现实事实。
- 尚不清楚的信息。
- 用户拒绝提供的信息。
- 现实约束。
- 相互矛盾的信息。
- 模型形成的分析假设。
- 各调查方向的完成程度。
- 报告交付要求的满足程度。

它是系统的状态管理层。

### 3. Adaptive Question Engine

负责决定下一道问题。

它读取当前 Decision Blueprint 和 Decision Context，识别当前最重要的信息缺口，然后在既定范围内生成问题。

它是系统的动态问答层。

### 4. Decision Readiness Engine

负责判断当前信息是否足以支撑正式报告。

它不以问题数量或问答轮数作为主要判断依据，而是检查：

- 关键调查方向是否已经充分了解。
- 必要信息是否已经获得。
- 关键矛盾是否已经解决。
- 重要未知项是否已经披露。
- 报告交付要求是否得到满足。
- 最终建议是否存在无法接受的证据缺口。

它是系统的充分性判断层。

# 第三部分：Decision Blueprint——初始调查蓝图

## 3.1 核心定义

Decision Blueprint 是每次决策问答开始时建立的调查范围和目标定义。

它不是问题列表，而是一个有边界的信息需求结构。

系统必须先知道要调查什么，再决定具体如何提问。

## 3.2 初始蓝图包含两个相互关联的领域

### A. Decision Investigation Blueprint

定义本次决策需要调查的方向。

每个调查方向至少包含：

| 字段 | 说明 |
|---|---|
| direction_id | 唯一调查方向 ID |
| name | 调查方向名称 |
| objective | 该方向需要弄清楚什么 |
| decision_relevance | 与最终决策的关系 |
| required_information | 必须获得的信息 |
| optional_information | 可选的辅助信息 |
| priority | P0 / P1 / P2 |
| completion_criteria | 满足什么条件可以认为已了解 |
| dependencies | 依赖的其他信息 |
| scope_boundary | 该方向允许调查的边界 |
| status | 当前状态 |

优先级定义：

- P0：直接影响决策结论的信息。
- P1：影响方案排序、风险或执行条件的信息。
- P2：辅助分析、提高个性化程度的信息。

P2 不得阻碍系统完成决策。

### B. Decision Deliverable Requirements（DDR）

定义最终报告必须完成哪些交付内容。

例如：

- 用户当前困境的结构化分析。
- 核心问题及其形成原因。
- 用户个人特征与当前决策的关联分析。
- 现实条件和关键约束。
- 不同决策路径的比较。
- 各方案的成本、风险和前提。
- 主推荐方案与替代方案。
- 低成本、可逆或分阶段验证路径。
- P6 验证实验。
- P8 后续 Continue / Adjust / Stop / Rerun 判断。

每项 DDR 应包含：

| 字段 | 说明 |
|---|---|
| ddr_id | 唯一交付要求 ID |
| deliverable | 需要交付的判断或内容 |
| report_page_id | 对应报告页面 |
| report_section_id | 对应报告章节 |
| required_dir_ids | 支撑该内容所需的 DIR |
| required_sources | 所需信息来源 |
| priority | P0 / P1 / P2 |
| completion_criteria | 完成条件 |
| status | 当前状态 |

DDR 和 Decision Context 必须保持语义独立。

DDR 代表最终报告需要回答什么。

Decision Context 代表系统目前掌握了什么信息。

二者通过 DIR 和信息来源建立关联。

## 3.3 调查范围锁定机制

这是本系统最重要的控制机制之一。

初始化后，系统必须形成明确的调查边界。

每个调查方向都有自己的 scope_boundary。

模型不能因为用户回答而任意增加新的调查方向。

如果用户回答中出现新的信息，系统需要判断：

1. 是否直接影响现有调查方向？
2. 是否影响 P0/P1 信息的完整性？
3. 是否会改变最终方案排序或推荐？
4. 是否属于现有方向下的必要子问题？
5. 是否确实需要增加新的调查方向？

只有满足明确的决策相关性，才允许调整蓝图。

### 新方向增加规则

新增方向必须经过范围变更检查。

新增申请需要包含：

- proposed_direction
- originating_fact_id
- related_decision_question
- decision_impact
- why_existing_directions_are_insufficient
- priority
- estimated_information_value

只有当新方向能够实质影响决策结果，并且无法合理归入现有方向时，才允许加入。

一般的背景补充、好奇心问题、知识延伸，不允许成为新方向。

新增方向原则上需要代码侧校验，并记录变更原因。

对于普通用户回答，默认优先更新已有方向，而不是创建新方向。

## 3.4 调查范围冻结与变更

初始 Blueprint 建立后，不代表永远不能调整。

但调整必须有记录。

允许：

- 调整方向优先级。
- 修改完成状态。
- 增加必要的子信息需求。
- 合并重复方向。
- 关闭已经不再相关的方向。

新增一级调查方向属于范围变更，必须通过明确的决策相关性检查。

任何范围变更都需要保留版本记录。

不得直接覆盖历史蓝图。

# 第四部分：动态提问与范围控制

## 4.1 动态提问的基本逻辑

每一轮的具体问题由 Adaptive Question Engine 生成。

其基本流程：

```text
读取当前 Blueprint
        |
读取当前 Decision Context
        |
读取 DDR / DIR 状态
        |
检查未满足的信息需求
        |
排除范围外问题
        |
计算信息优先级
        |
选择一个最重要的信息缺口
        |
生成一道具体问题
        |
等待用户回答
        |
更新状态
        |
重新评估
```

模型每轮主要负责生成一道最有价值的问题。

不允许一次性生成并执行全部问题。

## 4.2 问题选择优先级

问题优先级由以下因素综合决定：

1. 是否影响最终决策结论。
2. 是否影响主要方案排序。
3. 是否影响推荐方案的成立条件。
4. 是否存在未解决的关键矛盾。
5. 当前是否已经具备回答该问题的条件。
6. 该问题是否可以显著减少决策不确定性。
7. 是否存在成本更低、信息价值更高的提问方式。

原则上先解决 P0，再解决 P1，最后考虑 P2。

但如果 P1 信息是理解 P0 的必要前提，可以提前询问。

## 4.3 每轮问题数量

默认每轮只提出一个主要问题。

必要时可以在一个问题中加入简短的解释或限定条件，但不能把多个独立调查任务包装成一个问题。

系统应尽量避免：

- 一次询问五六个不同方面。
- 重复确认用户已经说过的信息。
- 机械地按照固定顺序提问。
- 用多个相似问题反复验证同一结论。

## 4.4 追问深度限制

动态提问必须设置明确的追问边界。

建议采用以下默认约束：

**每个调查方向最多进行 3 层有效追问，作为默认软上限。**

这里的层数是针对同一信息需求的深入程度，不是整个对话的问答轮数。

例如：

调查方向：创业动机。

第一层：了解用户为什么想创业。

第二层：区分创业兴趣与逃离当前工作的动机。

第三层：在存在实质不确定性时，询问一个可以验证两种动机的具体现实情境。

如果第三层之后仍然不能完全确定：

- 记录为未知或部分了解。
- 不再无限追问。
- 使用现有证据形成有边界的判断。
- 在最终报告中披露不确定性。

如果某个方向的决策重要性特别高，确实需要超过默认追问深度，必须说明原因，并由系统的规则层批准扩展，而不能由模型自行决定。

## 4.5 问题预算

问答系统需要设置整体预算，避免对话无限延长。

建议初始产品参数：

| 类型 | 建议有效回答轮数 |
|---|---:|
| 简单决策 | 5–7 |
| 中等复杂度 | 8–10 |
| 高复杂度 | 10–12 |
| 默认软上限 | 12 |
| 默认硬上限 | 15 |

以上为初始产品参数，需要通过真实用户测试调整，不是不可更改的业务常量。

注意：

- 只有有效回答轮次计入问答预算。
- 进度展示、状态修正、重复提交和技术错误不应计入。
- 用户主动补充的信息应更新状态，不应机械地当成新问题。
- 预算达到上限不代表信息已经充分。
- 如果关键问题仍然未知，不得强行将进度设为 100%。

到达硬上限时，系统应该评估：

1. 是否能够形成有条件的建议？
2. 是否存在无法解决的关键矛盾？
3. 是否有必要让用户选择继续补充信息？
4. 是否应该带着明确的不确定性进入报告？

不允许为了达到轮数上限而制造问题。

## 4.6 防止无限联想的硬性规则

必须在模型系统提示词和代码规则层同时实施。

模型必须遵守：

1. 只调查 Blueprint 中已有的方向。
2. 只追问与当前 DDR / DIR 直接相关的信息。
3. 每个问题必须说明对应的信息需求。
4. 不得把用户回答中所有新信息都转化为追问。
5. 不得将无关兴趣或背景话题加入调查。
6. 已满足的信息需求不得重复提问。
7. 已经达到完成条件的方向原则上停止追问。
8. 达到追问深度上限后停止深入。
9. P2 信息不得无限挤占 P0/P1 的调查预算。
10. 无法证明决策相关性的问题必须被拒绝生成。

建议在问题生成结果中增加：

- related_direction_id
- related_ddr_ids
- related_dir_ids
- information_gap
- decision_relevance
- why_this_question
- expected_information_gain
- depth_level

代码必须验证这些关联是否存在。

如果问题无法关联到有效的调查方向和信息需求，则不得发送给用户。

# 第五部分：Decision Context 数据体系

## 5.1 核心结构

新系统继续采用四层 Decision Context 结构。

```text
Decision Context
|
+-- Definition
|
+-- RealityFacts
|
+-- DecisionConstraints
|
+-- AnalyticalHypotheses
|
+-- Conflicts
|
+-- DIR
|
+-- Relationships
```

这四层的语义必须严格区分。

## 5.2 Definition：决策定义

记录用户真正面临的决策。

包括：

- concrete_event：具体事件。
- stakes：决策的重要性及潜在代价。
- desired_outcome：期望结果。
- decision_question：需要解决的核心问题。
- goal_priorities：目标优先级。
- unacceptable_outcomes：不能接受的结果。

Definition 应从用户原始表达中逐步形成，不得将模型推测直接写成用户确认的目标。

## 5.3 RealityFacts：现实事实

记录用户现实生活中的信息。

每项事实至少包括：

```json
{
  "fact_id": "FACT_xxx",
  "field": "字段名称",
  "statement": "事实内容",
  "status": "confirmed",
  "verification_level": "user_asserted",
  "source": "用户回答来源",
  "related_dir_ids": [],
  "timestamp": "记录时间"
}
```

允许的 status：

- confirmed
- unknown
- not_applicable
- declined
- unverified

允许的 verification_level：

- user_asserted
- user_estimate
- independently_verified
- none

有效组合：

| status | 允许的 verification_level |
|---|---|
| confirmed | user_asserted / independently_verified |
| unverified | user_estimate / user_asserted |
| unknown | none |
| declined | none |
| not_applicable | none |

禁止引入 inferred 作为 RealityFacts 的验证级别。

模型推断不能冒充用户事实。

`user_confirmed` 必须来自明确的用户确认事件及对应来源记录。

独立验证不等于用户确认。

## 5.4 DecisionConstraints：决策约束

记录影响用户选择的限制条件。

例如：

- 可用资金。
- 家庭责任。
- 时间限制。
- 地理位置。
- 合同或工作限制。
- 资源限制。
- 风险承受范围。

每项约束必须记录：

- constraint_id
- statement
- status
- verification_level
- source
- rigidity
- related_dir_ids

rigidity：

- hard
- soft

硬约束不能被模型自行忽略。

软约束可以进入方案比较，但必须保留其影响。

## 5.5 AnalyticalHypotheses：分析假设

记录模型形成的判断、假设和待验证解释。

例如：

- 用户可能主要受到工作压力驱动。
- 用户可能高估了项目的市场成熟度。
- 用户可能存在风险认知偏差。
- 某个资源不足可能是实际瓶颈。

每项假设必须包含：

- hypothesis_id
- statement
- supporting_evidence
- counter_evidence
- validation_need
- state
- related_fact_ids
- related_dir_ids

Hypotheses 不能直接写入 RealityFacts。

必须明确区分：

事实、用户主观判断、模型假设和待验证结论。

## 5.6 Conflicts：矛盾管理

不同回答之间出现冲突时，不得直接覆盖旧数据。

必须记录：

- conflict_id
- related_fact_ids
- field
- statement_snapshots
- source_records
- state
- resolution
- user_confirmation
- timestamp

state：

- open
- clarified
- unresolved_in_final

只有用户明确确认的解释才能将冲突标记为 clarified。

在最终 Freeze 时仍然存在的矛盾，必须标记为 unresolved_in_final。

## 5.7 DIR：Decision Information Requirements

DIR 用于描述每项决策判断需要掌握的信息。

每个 DIR 至少包括：

- dir_id
- serves_face / judgment
- need
- why
- category
- required_fact_roles
- current_state
- partial_satisfaction
- related_agenda_ids
- related_fact_ids
- lifecycle

current_state：

- known
- unknown
- conflict
- n_a

DIR 的状态不能简单根据问题是否问过、Agenda 是否完成来判断。

必须根据真实信息是否满足其所需角色进行聚合。

例如：

Agenda 全部完成，不代表 DIR 一定 known。

如果用户提供的信息仍然不足以支持判断，DIR 必须继续保持 unknown。

# 第六部分：个人分析系统——八字与紫微斗数

## 6.1 个人分析在新系统中的定位

Eastern OS 的差异化能力之一，是结合用户的个人分析基础与现实决策信息，提供真正个性化的决策分析。

新系统必须将本地个人分析能力纳入 Decision Intake 2.0。

个人分析不是普通聊天内容，也不是让模型每轮重新计算。

它是独立的数据输入层。

## 6.2 个人分析数据来源

现有八字及相关本地计算能力继续保留。

包括已有实现所覆盖的：

- 八字四柱。
- 五行结构。
- 十神。
- 大运。
- 流年。
- 神煞。
- 其他已有的命理派生数据。

包括现有紫微计算模块实际支持的：

- 十二宫结构。
- 命宫、身宫。
- 主星、辅星。
- 宫位关系。
- 大限。
- 流年及其他已有派生数据。

具体字段必须以仓库中实际计算模块和数据结构为准，不得仅凭概念自行假定已有计算能力。

## 6.3 统一 Personal Analysis Profile

每个计算结果必须保留：

- 数据来源。
- 计算模块。
- 计算版本。

- 输入数据版本。
- 数据可用性。

## 6.4 个人分析如何参与问答

系统不需要每一轮都展示个人分析。

正确流程：

1. 初始化时读取可用的 Personal Analysis Profile。
2. 判断哪些个人分析信息与当前决策有关。
3. 将相关信息作为辅助分析依据。
4. 如果发现具有实质价值的个人模式，可以在适当时机进行 Personal Pattern Insight 披露。
5. 如果该模式涉及现实行为或具体经历，需要通过用户回答验证。
6. 不相关的个人分析信息不参与本次决策问答。

个人分析不得无限扩展调查方向。

例如，用户讨论创业决策，系统可以关注与决策行为、风险偏好、资源使用、职业方向相关的个人分析维度。

不应该因此自动展开与本次创业决策无关的全部命理或紫微内容。

## 6.5 Personal Pattern Insight

在统一 Decision Understanding 信息框内设置个人模式洞察区域。

只有出现有价值的新洞察时才展示。

展示内容应包含：

- 个性化洞察。
- 对应的 POJU 自造术语。
- 与当前决策的具体关联。
- 必要的解释或现实验证问题。

不得为了展示传统分析能力而强行插入术语。

不得将传统命理或紫微分析表述成经过现代科学验证的客观事实。

## 6.6 POJU 自造术语转换

现有 POJU 自造术语翻译系统已经实现。

本次开发不重新设计、不重新实现该系统。

必须保留当前实现，包括：

- 原始传统术语识别。
- POJU 术语词典。
- 术语命名空间。
- 用户可见文本替换。
- 未知术语处理。
- 现有多语言机制。

新问答系统只需要正确调用现有转换管线。

模型内部可以使用八字、十神、大运、神煞、紫微斗数等原始术语。

用户界面输出必须经过现有术语转换流程。

不能因为重建问答系统而破坏现有术语替换能力。

# 第七部分：Decision Understanding 用户界面

## 7.1 整体交互原则

用户不应该感觉自己在填写一份长问卷。

整个过程应该像一个真正理解用户情况的高级决策顾问，逐步了解问题、提出针对性问题、展示阶段性理解，并不断调整分析方向。

界面需要同时传达：

- 系统已经理解了什么。
- 目前的分析方向是什么。
- 哪些信息已经明确。
- 哪些重要问题仍需了解。
- 当前正在询问什么。
- 当前决策理解进度如何。

## 7.2 统一信息框

在聊天输入框上方建立一个统一的 Decision Understanding 信息框。

建议结构：

```text
+------------------------------------------------+
| DECISION UNDERSTANDING                         |
|                                                |
| [=============---------] 68%                   |
|                                                |
| 当前理解                                         |
| 你目前面临的是……                                |
|                                                |
| 已经了解                                         |
| • 当前决策目标                                   |
| • 主要现实条件                                   |
| • 已确认的关键约束                               |
|                                                |
| 还需要了解                                       |
| • 当前影响方案排序的关键未知项                   |
| • 尚未验证的核心判断                             |
|                                                |
| Personal Pattern Insight                       |
| [有实质新洞察时显示]                             |
+------------------------------------------------+
| 当前问题                                         |
|                                                |
| 问题内容                                         |
|                                                |
| [输入框 + 三个快捷回复选项]                      |
+------------------------------------------------+
```

以上为结构示意，不要求完全照搬视觉设计。

必须保留现有三个快捷回复选项位于输入框内部的交互方式，不要将它们移动到输入框外面。

## 7.3 AgendaProgressPanel 改造

现有 AgendaProgressPanel 主要展示 Agenda 进度。

新系统需要将其改造为 Decision Understanding Panel。

不建议新建一个与原组件重复的进度组件。

可以保留原组件并重构其数据来源、计算逻辑和展示内容。

它需要展示：

1. Decision Understanding 进度。
2. 当前系统理解。
3. 已经了解的信息。
4. 仍然需要了解的信息。
5. Personal Pattern Insight。

## 7.4 进度计算规则

进度不能只根据问题数量或 Agenda 覆盖率计算。

应该根据：

- DDR 满足程度。
- P0/P1 DIR 完成程度。
- 关键事实和约束的确认状态。
- 关键矛盾状态。
- Sufficiency Gate 检查结果。

建议采用权重模型：

```text
Decision Readiness Progress
=
Σ（各项必要信息权重 × 满足程度）
/
Σ（必要信息总权重）
```

其中：

- P0 权重最高。
- P1 次之。
- P2 权重最低。
- 每个信息项只能按实际满足程度计分。
- unknown、declined、unverified 不能直接当成 confirmed。
- 已经不适用的信息可以按照规则标记为 N/A，但不能用来掩盖缺失信息。

具体权重应由代码统一管理，不能由模型每轮任意改变。

### 100% 的条件

只有当：

- 必要 DDR 已经满足。
- 关键 P0 DIR 已经达到要求。
- P1 信息缺口不会阻止可靠判断。
- 影响结论的关键矛盾已经解决，或已被明确纳入条件判断。
- Sufficiency Gate 通过。

才可以达到 100%。

如果信息仍然不足，进度不得为了视觉效果强行达到 100%。

进度百分比代表信息准备程度，不代表用户回答了多少问题。

# 第八部分：输入有效性与会话保护

## 8.1 正常的不确定回答

用户可能：

- 不知道答案。
- 不愿意透露。
- 暂时无法判断。
- 希望跳过。

这些都属于有效的用户响应，不属于滥用。

系统可以在第一次无法理解时换一种表达重新询问。

如果用户仍然不能回答，应允许：

- 不确定。
- 暂不回答。
- 拒绝提供。

并将相应信息记录为 unknown 或 declined。

这些状态必须在最终理解摘要中明确展示。

## 8.2 无效输入定义

本机制针对明显偏离当前问题的无效内容，例如：

- 与当前问题完全无关的内容。
- 无意义字符。
- 连续乱码。
- 明显无法形成有效回答的输入。
- 重复发送与当前问题无关的内容。

不能仅仅因为回答简短、表达方式不同或模型没有理解，就判定为无效输入。

系统需要区分语义相关性和答案完整程度。

## 8.3 三次锁定机制

按照产品设定执行：

```text
正常问答
   |
   v
首次无效输入
   |
   v
警告一次，重新提出原问题
   |
   v
第二次连续无效输入
   |
   v
锁定当前会话
   |
   +--> 冷却 10 分钟
   |
   +--> 会话保留 24 小时
   |
   +--> 10 分钟后显示 Continue
   |
   v
用户恢复会话
   |
   v
继续问答
   |
   +--> 再次出现连续两次无效输入
   |        |
   |        v
   |      再次锁定
   |
   v
累计第三次锁定事件
   |
   v
永久终止当前会话
```

规则：

- `invalid_streak`：连续无效输入次数。
- `lockout_count`：累计锁定事件次数。
- 有效回答后，`invalid_streak` 重置为 0。
- 两次连续无效输入触发一次锁定。
- 每次锁定事件增加 `lockout_count`。
- 第三次锁定事件触发永久终止。

10 分钟冷却时间与 24 小时会话保留时间是两个独立计时条件。

10 分钟后允许用户继续。

24 小时内未恢复的会话按过期规则处理。

会话过期不能自动算作第三次锁定。

## 8.4 付款与 PASS 规则

在用户开始付费决策问答前，必须明确披露：

- 本服务需要用户提供与决策有关的有效信息。
- 连续无效输入会触发会话锁定。
- 累计三次锁定事件将终止当前会话。
- 用户滥用行为导致的终止，按已披露的 PASS 规则处理，不自动返还 PASS。

该政策必须明确限定于用户滥用行为。

不能将其扩大为平台故障、服务未交付、系统错误或法律规定下的消费者权益一律不退款。

## 8.5 技术要求

无效输入保护必须在服务端执行。

不能只依靠前端按钮禁用。

锁定状态下：

- 不允许调用昂贵模型。
- 不允许更新 Agenda。
- 不允许改变正式 Decision Context。
- 不允许重复消耗 PASS。
- 不允许通过刷新页面绕过锁定。
- 不允许并发请求绕过锁定计数。

需要使用服务端状态、稳定幂等键和事务式状态更新。

# 第九部分：Sufficiency Gate、Freeze 与版本管理

## 9.1 Sufficiency Gate

Sufficiency Gate 判断是否具备生成正式报告的条件。

至少检查：

1. Decision Definition 是否足够明确。
2. P0 信息是否满足要求。
3. P1 信息是否足够支持方案比较。
4. 关键约束是否明确。
5. 影响结论的矛盾是否解决。
6. DDR 是否达到交付要求。
7. 重要未知信息是否有明确披露。
8. 主要方案是否有足够依据进行比较。

Gate 状态：

- PASS
- WARN
- FAIL

### PASS

信息足以支撑正式报告。

### WARN

存在未知信息，但不影响基本判断，或可以通过明确前提形成条件性建议。

### FAIL

存在阻止可靠判断的关键问题。

例如：

- 决定方案排序的关键矛盾尚未解决。
- 关键事实严重缺失。
- P5 核心方案无法进行有效比较。
- 数据版本或上下文哈希不一致。
- 报告关键内容没有任何可靠依据。

不能因为用户不愿意继续回答，就自动把 FAIL 改成 PASS。

## 9.2 最终理解确认

当系统判断信息已经足够，或者达到合理的调查终止条件后，生成完整的决策理解摘要。

摘要至少包括：

- 用户面临的具体决策。
- 用户真正想要的结果。
- 已经确认的现实事实。
- 已知的关键约束。
- 个人分析中与本次决策相关的内容。
- 当前主要判断与假设。
- 仍然未知的信息。
- 尚未解决的矛盾。
- 最终报告需要回答的核心问题。

用户可以：

- 确认。
- 修改。
- 补充。
- 指出理解错误。

修改后必须重新评估相关 DIR、DDR 和 Sufficiency Gate。

## 9.3 Freeze

用户确认最终理解摘要后，执行 Freeze。

Freeze 必须建立不可变的决策上下文版本。

正式报告只能读取冻结版本。

Stage 4 及后续报告生成流程不得修改已经冻结的 Decision Context。

## 9.4 Version 与 Hash

每个冻结版本至少记录：

- context_id
- context_version
- content_hash
- blueprint_version
- personal_profile_version
- created_at
- freeze_status

content_hash 必须覆盖规范化后的业务内容：

- Definition
- RealityFacts
- DecisionConstraints
- AnalyticalHypotheses
- DIR
- Conflicts
- 关键蓝图及交付要求版本

不应将纯 UI 状态、展示进度、时间戳或其他非业务字段随意混入内容哈希。

用户补充信息时：

- 原版本保持不变。
- 原版本标记为 superseded。
- 创建新的 draft 版本。
- 重新评估信息缺口。
- 新版本再次确认并 Freeze。
- 报告必须绑定明确的 context_version 和 content_hash。

不得静默覆盖历史冻结数据。

# 第十部分：模型调用与 Prompt 系统

## 10.1 全新模型调用架构

新问答系统需要自己的模型调用流程。

不应将旧 Call A / Call B 直接作为新系统的核心流程。

新系统模型调用建议分为以下职责：

### A. Initial Decision Understanding

首次理解用户的决策困境。

输出：

- 初始 Definition。
- 初始调查方向。
- 初始 DDR。
- 已知信息。
- 初始未知项。
- 初始调查边界。

### B. Decision Blueprint Initialization

建立正式的结构化调查蓝图。

这一过程可以通过一次或必要的模型调用完成，但不得将其设计成一次性生成全部具体问题。

它只负责确定调查目标、信息需求和方向。

### C. Adaptive Question Generation

每轮根据当前状态生成一道问题。

输入：

- 当前 Blueprint。
- 当前 Decision Context。
- 当前 DIR 状态。
- 当前 DDR 状态。
- 已经问过的问题。
- 当前调查预算。
- 范围限制。
- 个人分析中相关的信息。

输出：

- 下一道问题。
- 所属调查方向。
- 关联的信息需求。
- 提问原因。
- 预期信息增益。
- 问题深度。

### D. Answer Interpretation and State Update

解析用户回答。

输出：

- 新增或更新的事实。
- 约束变化。
- 新的分析假设。
- 冲突记录。
- 信息需求满足程度。
- 是否需要更新调查方向。

正式数据必须经过代码校验后写入 Decision Context。

### E. Decision Readiness Evaluation

根据当前状态判断是否继续调查。

不得让模型单方面宣布所有信息已充分。

最终状态必须由模型判断和代码规则共同决定。

### F. Final Understanding Summary

生成最终理解摘要，等待用户确认。

## 10.2 Prompt 必须重新统一设计

新系统需要重新整理生产环境实际使用的 Prompt。

必须先审查当前真正生效的 Prompt 入口，再进行重构。

已知之前审查发现：

- `lib/llm/prompts/poju-base.ts` 是现有主要基础 Prompt。
- `lib/llm/prompts/poju-base-v6.ts` 是 Shadow 实现。
- `lib/llm/phases/opening-phase-v6.ts` 也是 Shadow 实现。
- `oriental-prompt-context.ts` 仍然引用旧的基础 Prompt。
- `opening-phase.ts` 是现有实际 Opening 路径。

以上是此前审查时的代码状态，正式实施前必须重新核对当前主分支。

不能只修改 V6 文件，就认定生产 Prompt 已经改变。

# 第十三部分：状态一致性与事务要求

## 13.1 单一事实来源

Decision Context 必须有唯一正式数据来源。

不能同时存在两份互相独立、可能发生冲突的正式决策上下文。

临时模型输出可以进入缓冲区，但正式信息必须经过 DC API 写入。

## 13.2 双写一致性

如果新系统需要同步更新 Decision Context 和现有 ControlPlane：

必须保证操作的一致性。

采用：

```text
读取原始状态
    |
修改 Decision Context
    |
同步 ControlPlane
    |
持久化 Session
    |
成功：提交
失败：回滚
```

任一步骤失败，必须恢复到操作前状态。

使用稳定幂等键，避免重复请求导致重复写入。

不允许引入未经批准的新数据库或分布式事务系统。

在现有架构下，应优先利用同一个加密 IndexedDB Session Blob 完成提交与回滚。

## 13.3 报告绑定

报告必须绑定：

- context_id
- context_version
- content_hash
- personal_profile_version
- report_version

不能在报告生成期间读取不断变化的未冻结数据。

# 第十六部分：最终架构定义

Eastern OS / POJU 的新决策问答系统，正式定义为：

**Decision Intake 2.0 是一套以用户当前决策目标为中心，以预先确定的调查蓝图为边界，以 Decision Context 为信息基础，通过动态问题生成和状态机持续调整调查路径，并以 Decision Readiness 作为结束条件的统一决策信息收集系统。**

它不是普通聊天机器人。

它不是固定问卷。

它不是按轮次推进的阶段式咨询流程。

它也不是由模型自由联想、不断扩展问题的开放式对话。

它是一套具有明确目标、明确调查范围、明确完成标准和严格状态管理的决策信息收集系统。

其核心工作原则是：

1. 先明确本次决策要解决什么问题。
2. 先建立调查方向和报告交付要求。
3. 不预先生成全部问题。
4. 每轮根据真实信息状态决定下一道问题。
5. 所有问题必须属于既定调查范围。
6. 允许动态调整，不允许无限扩展。
7. 现实事实、决策约束和模型假设严格分离。
8. 八字与紫微斗数本地计算共同进入个人分析基础。
9. 保留现有 POJU 自造术语转换系统。
10. 根据真实信息充分性决定何时结束。
11. 最终理解必须经过用户确认。
12. 冻结上下文后才能生成正式决策报告。
13. 所有重要判断必须具备信息来源和追溯关系。

**最终目标：让用户通过一段有限、连续、个性化且有明确边界的对话，完成一次真正充分的决策理解，并获得有依据、可执行、可验证的正式决策方案。**

# 补充章节：Understanding-Driven Adaptive Question Engine

## 1. 核心定义

Decision Understanding 不只是面向用户的进度展示组件，而是新问答系统每轮提问前必须执行的结构化决策理解机制。

系统必须先理解当前已经掌握的信息、仍然存在的信息缺口，以及这些信息与最终决策目标的关系，然后才能决定下一道问题。

用户界面展示的 Decision Understanding 与模型问题规划所使用的 Decision Understanding State，必须来自同一套结构化数据。

不得让 UI 总结与模型实际使用的状态分别独立生成。

## 2. 每轮必须完成的五项工作

### 2.1 Current Understanding

更新当前对用户决策困境的整体理解。

包括：

- 当前具体事件。
- 用户真正希望解决的问题。
- 用户的核心目标。
- 当前决策面临的主要矛盾。
- 已经形成的阶段性认识。

只在出现实质变化时更新，不得机械重复。

### 2.2 Understood

整理已经掌握的信息。

包括：

- 已确认的现实事实。
- 已知的决策约束。
- 已经明确的用户目标。
- 已经达到完成标准的调查方向。
- 已经获得充分支持的判断依据。

每项信息必须保留来源及其验证状态。

### 2.3 Need to Understand

识别仍然需要了解的信息。

包括：

- 尚未满足的 P0/P1 信息需求。
- 影响决策排序的未知项。
- 需要进一步验证的假设。
- 尚未解决的关键矛盾。
- 报告交付要求中的信息缺口。

必须区分真正必要的信息和可选补充信息。

不得为了追求信息完整而无限增加调查需求。

### 2.4 Personal Pattern Insight

检查八字、五行、十神、大运、神煞及紫微斗数本地计算数据中，是否存在与当前决策直接相关的新洞察。

必须遵守：

- 只使用实际可用的个人分析数据。
- 只披露与当前决策有关的洞察。
- 保留现有 POJU 自造术语转换管线。
- 说明该洞察与当前决策的关联。
- 区分传统分析解释与现实验证事实。
- 不强制每轮生成洞察。
- 没有实质新洞察时不展示该模块。

### 2.5 Next Question Planning

从当前未满足的信息需求中选择下一道最有价值的问题。

必须明确：

- 关联的调查方向。
- 关联的 DDR / DIR。
- 当前信息缺口。
- 提问的决策价值。
- 为什么现在询问。
- 预期获得的信息。
- 当前追问深度。
- 是否符合调查范围和问题预算。

所有问题必须通过范围和状态校验。

## 3. 内部执行顺序

```text
User Answer
    |
    v
Answer Interpretation
    |
    v
Update Decision Context
    |
    v
Update Current Understanding
    |
    v
Update Understood
    |
    v
Update Need to Understand
    |
    v
Evaluate Personal Pattern Insight
    |
    v
Next Question Planning
    |
    v
Scope / Depth / Budget Validation
    |
    v
Generate Next Question
```

Decision Readiness Engine 应在每轮同步检查是否已经满足结束条件。

如果满足充分性条件，则进入最终理解确认，不再强制生成下一道问题。

## 4. 数据一致性要求

Decision Understanding State 不得成为独立于 Decision Context 的第二套事实数据库。

其内容必须能够追溯到：

- Definition。
- RealityFacts。
- DecisionConstraints。
- AnalyticalHypotheses。
- Conflicts。
- DIR。
- DDR。
- Personal Analysis Profile。

Understood 和 Need to Understand 可以作为基于上述数据计算出的展示与调度视图，但不能取代正式数据源。

Current Understanding 可以包含模型综合判断，但必须标明判断性质，不能冒充用户确认的事实。

## 5. UI 与模型共用原则

统一 Decision Understanding Panel 展示：

1. Current Understanding。
2. Understood。
3. Need to Understand。
4. Personal Pattern Insight。

模型在生成下一道问题前必须读取对应的结构化状态。

UI 不应自行推测信息状态，也不应通过问题数量生成进度。

## 6. 验收标准

- 每次生成下一道问题之前，必须完成当前状态整理。
- 下一道问题必须能够追溯到明确的信息需求。
- 用户回答后，系统能够更新当前理解。
- 已确认信息不会被重复当作未知信息。
- 模型假设不会被写成用户事实。
- 个人分析洞察只在与当前决策有关时展示。
- 没有新洞察时不强制展示。
- 已经满足完成标准的调查方向停止追问。
- 超出调查范围的问题不能发送给用户。
- Decision Understanding UI 与模型调度读取同一状态源。
- 达到充分性条件后进入最终理解确认，而不是继续生成问题。
