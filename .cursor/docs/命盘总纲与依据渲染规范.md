**背景**：现有依据生成有两条并行的病灶——① 同一自造术语在不同页面被反复复用同一角度（如"流展"在P3/P4/P4三处近乎同义重复）；② 试图在单句里塞入多元素五行生克关系时，渲染逻辑崩溃，产出`【火】【水:水】`这类半渲染残骸（样本 L383）。本方案把"这个人命盘的结构性事实"从"报告每页当下要说什么"里拆出来，独立成一份**命盘总纲**，报告页面转为对总纲的动态引用，而不是每页各自重新演算一遍命理批断。

## 一、命盘总纲（Thesis Dimensions）设计

### 1.1 定位

总纲 = 对这个人 structured 真算数据的**一次性收敛诊断包**，供后续所有报告页面的 assign 阶段检索引用，不是新增一页展示给用户的"古典批断墙"（虽然可以选择性地把其中打磨过的结论摘要展示在 P1 开篇或 P7 附录，但那是可选的展示层，不是总纲本身的必需用途）。

### 1.2 维度划分：固定6-8个结构维度，不对应报告的16个依据段落

总纲按"这个人命盘里恒定不变的结构性事实"分类，而不是按"报告当前要回答什么问题"分类。参考本次分析样本，大致应覆盖：

| dimension_id | 维度名 | 对应传统命理概念 | 覆盖内容 |
|---|---|---|---|
| `day_master_strength` | 日主强弱与格局 | 日主旺衰、月令、帮身 | 这个人整体的"底子厚不厚" |
| `favor_avoid_tuning` | 用神喜忌与调候 | 用神、忌神、燥湿平衡 | 什么状态对他有利/不利，需要什么来平衡 |
| `interpersonal_pattern` | 十神组合与人际模式 | 七杀/正印/比肩等 | 合作、竞争、话语权类议题的根源 |
| `cycle_rhythm` | 纪元与岁环节奏 | 大运、流年 | 当前处于哪个阶段，节奏该冲还是该守 |
| `resource_pattern` | 财帛与资源模式 | 财星、食伤生财 | 攒钱难不难、资源怎么分配 |
| `expression_creativity` | 表达输出与创造力 | 食神伤官 | 专业输出、创造力这条线的底层动力 |

维度数量不强制刚好6个，但应该收敛在6-8个左右——如果某个具体案例的维度膨胀到十几个，大概率是维度切分粒度不对，需要合并；如果长期只能凑出3-4个，需要检查真算数据本身是否给够了信息。

### 1.3 每个维度的字段结构与真算数据核对清单

**核心原则：本规范只规定每个维度"必须核对真算数据里的哪几类字段"，不规定具体判断内容写成什么样。** 具体判断内容100%由这个用户实际的真算结果决定——不同用户在同一维度下，`classical_basis`和`conclusion_zh`的具体内容应该完全不同，因为命盘不同。规范里如果出现任何示例文本，仅作"格式/颗粒度参考"，**不得被当作内容模板去套用或凑数**。

字段结构：

```json
{
  "dimension_id": "day_master_strength",
  "dimension_name_zh": "日主强弱与格局",
  "classical_basis": { "...见下方该维度的核对清单，逐项填写..." },
  "conclusion_zh": "（走通顺白话连接层写成的完整段落，内容完全来自左侧classical_basis的真算核对结果，不得引入清单之外的判断）",
  "usable_claims_hint": ["由本次真算实际结果推出的适用场景标签，不预设"],
  "wuxing_relations": [
    { "from": "...", "to": "...", "relation": "...", "note": "..." }
  ]
}
```

**每个维度对应的真算数据核对清单**（以下"清单项"是必须核对的类别，不是必须出现的具体结论——如果某一项真算没有对应输出，`classical_basis`里该项必须如实写"未见相关特征/未成局"等否定性描述，**不得为了凑叙事完整度而编造**）：

| dimension_id | 必须核对的真算数据类别 |
|---|---|
| `day_master_strength` | ①日主与月令的生克关系（当令/失令，无论结果如何）②四柱中日主同类/异类的分布（帮身多还是耗身多）③地支有无合局、刑冲对根气的影响（有则说明是什么局，无则如实写未成局）④综合旺衰判断（必须由①②③推出，不能跳过举证直接给结论） |
| `favor_avoid_tuning` | ①真算给出的喜用神具体是什么（不预设一定是"金水"或任何特定组合）②真算给出的忌神/需回避的状态是什么③当前命局是否存在真算标注的燥湿/寒暖失衡（有则说明失衡方向，无则如实写"局中相对平衡"） |
| `interpersonal_pattern` | ①真算实际给出的、与人际/合作相关的十神是哪几个（可能是七杀、正官、比肩、伤官中的任意组合，不预设）②该十神有根还是虚浮（必须核对，这是专业度的关键分水岭，不能省略）③该十神对日主构成的具体作用方向 |
| `cycle_rhythm` | ①真算给出的当前纪元（大运）阶段特征②真算给出的当前岁环（流年）特征③二者叠加后的具体作用（是加强还是缓解，由真算结果决定，不预设方向） |
| `resource_pattern` | ①真算给出的财星状态（旺/弱/无根，如实反映）②真算给出的食伤生财链路是否成立③资源分布相关的具体十神组合 |
| `expression_creativity` | ①真算给出的食神/伤官具体状态②真算给出的表达输出相关十神是否有根 |

**如果某个具体用户的真算数据，在某个维度下确实找不到任何有效核对项**（比如财星完全无根且食伤链路也不成立），`classical_basis`应该如实体现"这个维度在此人命盘中特征不明显"，`conclusion_zh`也应该相应写得简略甚至跳过深入展开——**这是真实信息的一部分，不是要补写的缺口**，不得为了让六个维度篇幅均衡而编造内容去填满。

### 1.4 维度间的生成顺序与依赖关系

`day_master_strength`（日主强弱与格局）必须最先生成，因为其它维度的判断在传统命理逻辑里依赖这个前提——比如`favor_avoid_tuning`（用神喜忌）里"某个十神是喜是忌"，取决于日主是身强还是身弱这个前提，身强身弱结论不同，喜忌方向可能完全相反。

**落地要求**：`favor_avoid_tuning`和`interpersonal_pattern`在生成`classical_basis`时，必须显式核对并引用`day_master_strength`已经得出的`strength_verdict`作为前提条件，确保六个维度合起来读是一套自洽的诊断，不会出现互相矛盾（比如一个维度说身强、另一个维度却按身弱的逻辑推导用神方向）。

### 1.5 用户议题与期望方向的作用边界（合规红线，不可绕过）

总纲生成前，会拿到这次咨询的议题/困境/期望方向（来自collecting阶段）。这个信息**只允许影响一件事：六个维度里，哪几个该展开写得详尽、哪几个可以相对简略**——比如这次议题是"要不要辞职创业"，`resource_pattern`和`cycle_rhythm`就该优先详尽展开，而跟这次议题关系不大的维度可以简略处理。

**绝对不允许发生的事：议题反过来影响任何一个维度内部的具体判断内容。** 日主是否身强、七杀是否有根、局中是否燥气偏重——这些判断只能由真算结果决定，不能因为"用户在纠结创业焦虑"，生成的时候就顺势找一个"能support创业焦虑"这个叙事的判断写进去。如果放任议题影响真算判断的内容，就是从"真算驱动的批断"滑向"为了讲用户想听的故事而编数据"，这正是项目定位里明确要拒绝的宿命论/迎合式话术，必须在设计和验收上都守住这条线（见第五节验收清单新增项）。

### 1.6 生成与打磨要求

- 每个维度独立走一次"去掉测试"：如果去掉这个维度，是不是有其他维度已经在结构性事实里表达一样的意思，是则合并；
- 允许人工复核这6-8段——因为只需要写一次，值得比现在报告里16段依据更高的打磨精度；
- 总纲整体应该达到专业命理批断应有的举证深度：每一步判断都能追溯到具体的真算数据支撑，不是笼统印象式描写，也不需要读者去猜论据是什么。

## 二、报告依据如何引用总纲

### 2.1 assign 阶段的新契约

每条 claim 的信号不再是裸的 `slug`，改为：

```json
{
  "claim_id": "safety_buffer_anxiety",
  "claim_zh": "财务安全垫的焦虑",
  "necessary_signals": [
    {
      "dimension_id": "resource_pattern",
      "inference_zh": "本次针对这个claim，从该维度推导出的具体结论——必须是新的、针对当下问题的推论，不能是conclusion_zh的复制粘贴",
      "role": "解释'为什么攒不下钱'",
      "why_needed": "去掉此信号，无法解释收入不低却存不住这个具体现象"
    }
  ],
  "removal_test": { "passed": true, "notes": "..." }
}
```

`inference_zh` 是这次改动的关键新增字段——它要求模型**每次引用总纲维度时，都必须针对当下这个具体claim重新做一次推论**，而不是简单复制总纲里已经写好的`conclusion_zh`。这个字段直接决定了"流展被引用三次但说的都是一句话"这类问题能不能被拦下来（见2.3）。

### 2.2 缺总纲出处时的处理：先扩总纲，不许 write 阶段现编

如果 assign 阶段发现某个 claim 需要的结构性事实，在现有总纲的6-8个维度里找不到对应（`usable_claims_hint`匹配不上，`wuxing_relations`也没有覆盖），**正确流程是触发总纲扩展**：给总纲补一个新维度，或者细化某个已有维度的`wuxing_relations`/`usable_claims_hint`，扩展完成、经过和1.4节一样的打磨要求后，再回到 assign 继续往下走。不允许 write 阶段绕过总纲直接现编一个从未被验证过的结构性说法。

### 2.3 哪些内容不需要总纲出处

**只有"为什么"层面的结构性归因，才需要总纲出处**。用户自述的现实处境——比如"每周只能挤出5-8小时""安全垫大概6-12个月""旧部希望我全职加入"——这些是事实性输入（来自collecting阶段的用户回答），不是命理结构性依据，**可以直接写，不需要在总纲里找对应**，也不受本方案的removal_test约束。

### 2.4 同一维度被多段引用：允许，但卡住"同维度+近似推论"

一个真正的顾问，本来就会用同一套对这个人的结构性理解，去回应很多个不同的具体问题——这是"真的懂这个人"的表现，应该允许。**要拦截的不是"这个维度被引用了几次"，而是"每次引用有没有针对当下这个claim讲出一个新的、具体的推论"**。

具体检查：对同一个`dimension_id`的所有引用，做`inference_zh`之间的语义相似度检查（复用此前"role Jaccard"的检查逻辑，检查对象从孤立信号换成`inference_zh`），过高则判定为复用失败，打回重试，要求换一个针对当下claim的具体切入角度。

**用样本里的例子验证一下这套规则该怎么判**：
- 三次引用"流展"（L311、L357、L396）现在的`inference_zh`分别是"能把经验变成产品""技术底蕴与从容输出能力""开创性的输出能力"——这三句话语义高度重叠，应该被这道闸拦下来，要求重写出三个真正不同的具体推论（比如"这次针对产品化claim，重点讲流展让你有能力做标准化交付"；"针对角色定位claim，重点讲流展让你能在合作中提供不可替代的技术话语权"，两者的落点应该明显不同）。

### 2.5 页面结构：核心方向固定，段落数量动态，不为凑数硬写

P1（核心直答）/P2（归因剖析）/P3（破局策略）/P4（自我调频）……每页的**核心职能固定**（比如P2固定回答"为什么这些表象背后有结构性原因"），但具体这一页要挂几个claim、每个claim引用总纲哪个维度，**不再是固定的段落数量模板，由总纲的实际内容和assign的动态匹配结果决定**。如果按当前这份总纲，某一页真正站得住的独立claim只有3个，就只写3个，不强行凑够历史上惯用的段落数，这是防止"硬凑"重新出现的关键约束。

## 三、五行与关系链的渲染规则

### 3.1 规则一：金木水火土允许出现，但换一条渲染通道

不采纳"不输出五行字"这个方向——理由是L383的根因不是"写了个水字"，而是**多元素生克关系被塞进一套"变量括号拼接"的模板逻辑**（现在产出`【火】【水:水】`这种半渲染残骸的那条通道），普通单字点缀（如"锚元所对应的水"）走的是另一条已经跑通的"闭集术语通顺白话连接"通道，从未出问题。

**落地要求**：废弃"变量括号拼接"这条独立通道，把五行字和关系链的表达，**统一并入现有闭集术语的白话连接生成逻辑**——也就是说，模型写"火耗水"的时候，应该像写"岁环带来周期性压力"一样，把它当成一段需要组织成自然语言的内容去写，而不是套用`【元素A】动词【元素B】`这种模板拼接。

### 3.2 规则二：单点点缀与关系链分档管理，关系链设复杂度上限

- **单点点缀**（比如"锚元所对应的水"）：现有通道处理良好，不改；
- **关系链**（多个五行元素之间存在生克关系）：设置单句/单claim的复杂度上限——建议一句话最多容纳2个元素+1种关系，超过就必须拆分。

**用L383做一次具体的拆分示范**：

原文（崩溃版，6要素挤在一段）：
> "岁环由此先带动这一层变化岁环带来的由此先带动这一层变化【火】特质正在大量消耗你的【水:水】资源……纪元里的再托住后面这一段节奏【金】对上眼前这一头选择【水】虽然能给你一些支撑，但【金】也会对衔接到这一环现实压力【木】形成制约……"

拆分后（建议方向，2个独立claim，各自1-2个元素关系）：
> claim A（对应dimension: cycle_rhythm + favor_avoid_tuning）："当前这段岁环带来的旺盛干劲，正在持续消耗你原本就不多的沉静储备，让你感到精力被透支。"
> claim B（对应dimension: favor_avoid_tuning）："眼下能给你托底的那股支撑力量，同时也在无形中压缩你面对现实压力时的腾挪空间，这提示你此刻不宜强攻，该先守住节奏。"

两句话各自独立、通顺、可读，且每句只承载一组关系，不需要在一句话里塞完整条生克链。

### 3.3 规则三：正文契约不变，关系链主要留在依据折叠层

- 正文（策略/行动板块）继续保持行为/精力白话为主，不直接暴露五行关系链，这条不变；
- 五行关系链的完整表达，限定在"底层依据"这个用户需主动展开才可见的折叠层；
- **落库前必须过一道半渲染残骸检测**：正则扫描`【】`包裹的裸字符、未闭合的`⟦w:⟧`标记、以及"由此先带动这一层变化"这类连接模板词是否在同一段落里出现2次以上（这是L383里模板重复插入的具体特征），命中则直接拦截，不许进入交付库，走重试而不是带着残骸交付。

## 四、与现有系统对接

- 总纲不是新开一页展示内容，是给 assign 阶段新增的一个可检索数据源；
- **assign**：`claim → dimension_id + 本次 inference_zh`；缺结构性事实时走"总纲扩展"流程，不允许 write 阶段现编；
- **write/mark**：引用总纲的 `conclusion_zh` 和 `wuxing_relations` 组织成白话表达；关系链一律走"通顺句生成"，不再走`【木】【火】`模板拼接这条旧通道；
- 现有的跨页 `prior_signal_roles` / role Jaccard 检查机制沿用，只是检查对象从"信号本身"升级为"`dimension_id` + `inference_zh`的组合"。

## 五、验收清单

- [ ] 总纲维度数量落在6-8个区间；每个维度过一次"去掉测试"确认不冗余
- [ ] 抽查总纲每个维度的 `conclusion_zh`，人工确认每一步判断都能追溯到具体真算数据支撑，不是印象式描写
- [ ] 抽查至少一个"某维度真算核对项为空"的真实案例，确认 `classical_basis` 如实写了"未见相关特征"类否定描述，而不是编造内容凑满
- [ ] 维度依赖顺序：抽查 `favor_avoid_tuning`/`interpersonal_pattern` 是否正确引用了 `day_master_strength` 的 `strength_verdict` 作为前提，六维之间无互相矛盾
