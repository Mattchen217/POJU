# LAB 全流程测试 · 首次操作手册

> **给谁看**：第一次用 Delivery Lab「全流程测试」的人（产品 / 运营 / 工程手测）。  
> **这页做什么**：一条 lab 从 **Stage1–3 聊天**（看完整 call_trace、可重跑）→ 自动灌入盘源 → 再跑 **交付 + Companion**（逐步 Run → 审 → Approve）。  
> **配套**：质量打分尺见 [`pivot-全流程手测评测标准.md`](./pivot-全流程手测评测标准.md)；交付逐步人审见 [`交付v3-Lab人审与升闸操作手册.md`](./交付v3-Lab人审与升闸操作手册.md)。  
> **入口**：`/ops` 登录 → `/ops/delivery-lab` → 选「全流程测试 Stage1–3 + 交付」。

最后更新：2026-10-13

---

## 0. 先建立正确心智（必读）

| 阶段 | 怎么测 | 发现问题怎么办 |
|------|--------|----------------|
| **Stage1–3**（上方 Pipeline 聊天区） | 聊一句 → **立刻**看右侧完整 trace（喂料 / system / user / reasoning / 输出） | **不要**找 Approve。有问题 → 改提示词/喂料后点「重跑本轮」，或继续输入/点芯片 |
| **Stage4 交付**（下方步骤列表） | 逐步 **运行** → 审 trace → **本步通过** | 闸不过 / 人眼不过 → 记类别 → 改生成侧 → 准备重跑；**禁止带病解锁下游** |

一句话：上面是「对话实验室」；下面是「交付质量闸」。两条链路不要混用修法。

## 1. 怎么设计问题（测什么才有意义）

### 1.1 好题的共同标准

一条题干尽量同时满足：

1. **单楔**：一件具体事（不要「工作+感情+搬家」三件绑一起）。  
2. **有处境**：时间 / 角色 / 约束至少有一点（别只写「我很迷茫」）。  
3. **有期望**：想推向的结果可检验（别只写「变得更好」）。  
4. **路径意图清楚**：你这轮要测 `solo`、还是二元 `dyad`、还是「跳过对方盘」。

### 1.2 建议必跑的问题类型（至少各 1 条）

与手测评测矩阵对齐，LAB 里优先跑齐：

| # | 类型 | 题干怎么写 | 期望 path | LAB 上怎么操作 |
|---|------|------------|-----------|----------------|
| **A** | 非二元 · 事业/决策 | 只有「我」：接不接项目、转不转行、要不要裸辞；写清期限与代价 | `solo` | 正常聊到理解门 → 确认；不应无故弹收对方盘 |
| **B** | 二元 · 收对方盘 | 「我与**某一个**具体人」（伴侣/合伙人）+ 共同决策期望 | `dyad` | 出现二元门 → 粘贴对方 `base_analysis` JSON →「收集对方盘」→ 再确认理解 |
| **C** | 二元 · 跳过对方盘 | 同上议题 | `solo`（有二元信号但无对方盘） | 点「跳过对方盘」→ 确认理解；后文不得编造对方八字 |
| **D** | 三人及以上（边界） | 「我、A、B 三人怎么合」 | **拒识/收成二人或单人** | 不应进伪多元真算；应引导收敛 |
| **E** | 身份/能力 | 「你是谁 / 你能算什么」 | Eastern OS 口径 | 不提 Pivot；不恐吓式占卜 |

可选加测（有时间再跑）：

| # | 类型 | 目的 |
|---|------|------|
| F | 空期望 / 多楔糊题 | 看模型是否追问期望、是否硬推 Stage2 |
| G | 中途改口（确认后想补充） | 理解门点「补充」再确认是否干净 |
| H | 收集阶段芯片短答 | 模型是否接住芯片、是否闲聊跑题 |

### 1.3 题干模板（可直接改数字）

**A · solo 决策**

> 我在现公司做产品第 4 年，下周前要决定要不要接一个外包项目（约 3 个月、收入可观但几乎占满夜晚）。期望是：保住本职不被开，同时不把身体拖垮；如果只能选一个，先稳住现金流。

**B/C · 二元**

> 我和合伙人（一个具体人）在是否把工作室融资里谈崩了：他要激进扩，我想先回本。期望是：90 天内谈成一个双方都能签字的节奏，而不是谁赢谁输。

**D · 拒识**

> 请帮我合一下我、太太、丈母娘三个人的盘，看看今年搬家谁说了算。

## 2. 第一次上 LAB：从零到跑通（逐步照做）

### 2.1 准备

1. `/ops` 用 ops 账号登录。  
2. 准备被测人的**出生信息**（年月日、时分、出生城市、性别）。  
3. （可选）二元用例再准备对方盘 JSON，在详情页二元门里粘贴。

### 2.2 创建全流程 Lab

1. 打开 `/ops/delivery-lab`。  
2. 选 **「全流程测试 · Stage1–3 + 交付」**（此模式只显示出生信息表单）。  
3. 填写：出生日期（年/月/日）、出生时间（时/分）、出生地点（搜索选城市）、性别。  
4. 点 **「创建全流程 Lab → 进入聊天测试」**（浏览器本地排盘 → 进详情页）。  
5. **不必**填问题 / breakthrough_core / agenda——那些在详情页聊天里产生。

### 2.3 上方 Pipeline（Stage1–3）怎么测

页面结构：

| 区域 | 作用 |
|------|------|
| 阶段提示条 | 当前 cursor / path / 下一步该做什么 |
| 左：迷你聊天 | 消息、芯片、理解门/二元门/汇总确认按钮、输入框 |
| 右：Call Trace | 本轮完整喂料 / system / user / reasoning / 输出 / meta（Stage1–3 每轮必看）；Call A 可切换 dims/spine/voice 多腿；Stage2 Call A/B 为 **high**（非 xhigh） |
| 工具条 | **重跑本轮**、job 运行中可 **刷新 job** |
| 下方交付区 | 未解锁时灰显；Synthesis 成功后解锁 |

**推荐节奏（solo 一路）：**

1. 在输入框贴上 A 类题干 → 发送。  
2. 等回复出现 → **先看右侧 trace**（是否喂对盘、system 是否串阶段、reasoning 是否瞎编）。  
3. 满意 → 点芯片或继续打字；不满意 → **重跑本轮**（或记下问题再改代码后重跑）。  
4. 到理解门 → 点 **「确认理解 → Call A」**（若还想改理解，点补充说明再聊）。  
5. 等 Segment2 job（提示条会显示 pending；可点「刷新 job」）。Call A 完会自动起 Call B。  
6. 进入 Collecting → 用芯片/短答把议程答到能收口。  
7. 到汇总确认 → 点 **「确认汇总 → Synthesis」**，等 job 完成。  
8. 成功后提示 **delivery unlocked**，下方交付步骤可点。

**二元跳过一路（C）：** 题干写出具体他人 → 出现「跳过对方盘」→ 点跳过 → 再确认理解。看 path 是否为 `solo`。  
**二元收集一路（B）：** 粘贴对方盘 JSON →「收集对方盘」→ 确认理解。看 path 是否为 `dyad`，后文是否用合盘摘要而不是编造。

### 2.4 下方交付区（Stage4）怎么测

解锁后与「交付-only」Lab 相同：

1. 从当前 cursor 步点 **运行**（LLM 步可能要数分钟）。  
2. 右侧看该步 call_trace / 产物。  
3. 机闸 + 人眼都过 → **本步通过**；不过 → **不要 Approve**，改提示/喂料后准备重跑。  
4. 细尺与升闸流程见交付人审手册，不要在 LAB 聊天区「凑合过」。

### 2.5 建议记录模板（每条用例抄一份）

```
日期：
Lab ID：
用例类型：A/B/C/D/E
题干：
path 预期 / 实际：
Stage1 观察（理解门 / 二元门 / 否决项）：
Stage2 观察（Call A 可见质量 / Call B 议程是否倒逼交付）：
Stage3 观察（收集是否对准、是否跑题）：
Synthesis / seed 是否解锁交付：
交付前三步（bootstrap/thesis/…）人审结论：
LAB 页 bug？（是/否 + 复现）
模型/喂料问题？（类别一句话）
下一步动作：改代码位置 / 重跑哪一轮
```

## 3. 出问题怎么修：两类分开

先问自己一句：**是「页面/接口坏了」还是「模型内容不对」？**  
修法完全不同。

---

### 3.1 类型一：LAB 页本身的问题（工具坏了）

症状像「点了没反应、灰死、报错、job 一直转、交付永远锁」。优先当工具 bug，不要先改提示词。

#### 常见现象 → 怎么判断 → 怎么处理

| 现象 | 可能原因 | 你怎么做 |
|------|----------|----------|
| 创建页扫不到本机盘/会话 | 域名不一致、隐私模式、IndexedDB 空 | 到聊天页 Application→IndexedDB 看 `pojulife_v4`；换与聊天相同 origin；或手贴 `base_analysis` |
| 创建失败 `need_base_analysis` / `need_structured` | JSON 不是对象或没有 structured | 用导入档案；或确认粘贴含 `structured`（日主/四柱等） |
| 发送后一直 busy / 503 | OpenRouter 未配、排队、超时 | 看 ops 网络面板与服务端日志；确认 `OPENROUTER_API_KEY`；稍后重试同一句 |
| 理解门点确认报 `not_awaiting_understanding_confirm` | 阶段还没到门 / 会话镜像不同步 | Refresh 页面；若 cursor 不是 awaiting_understanding，继续聊到门再点 |
| job 一直 pending | 后台 `after()` 未跑完或挂了 | 点「刷新 job」；再点 jobs 的 kick（POST segment2/synthesis）；看服务端 `[lab-gate]` / `[lab-jobs]` 日志 |
| 交付区一直灰、提示 locked | Synthesis 未成功 seed | 看 cursor 是否 `ready_for_delivery`、`pipeline_delivery_unlocked`；Synthesis 失败看 turn 的 error，修完后重新确认汇总 |
| 点交付 Run 得 `pipeline_delivery_locked` | 同上，前端灰显被绕过 | 先跑完 1–3；不要手改 KV 强行解锁带病交付 |
| 重跑本轮无效 / `no_chat_turn_to_rerun` | 最后一轮不是 chat（是 gate/job） | 只对「聊天轮」重跑；gate/job 失败用对应 gate/jobs 重试 |
| 芯片点了发出去但模型当没看见 | 多为模型侧；若消息列表没出现 user 气泡 | 先确认左侧是否出现你的芯片文案；没有则属 UI/API |
| Trace 右侧空白 | 该 turn 无 attempt.call_trace（旧数据或非 LLM 步） | 选中有 chat/segment2/synthesis 的 turn；chat 轮应有 system/user |
| 刷新后聊天没了 | Lab KV TTL（约 48h）或换了环境 KV | 重新创建 lab；本地无 Upstash 时注意多实例内存 KV 不共享 |

#### LAB 工具问题的修复原则

1. **先复现**：Lab ID + 操作顺序 + 接口返回 `error` 字段 + 浏览器 Network。  
2. **先分界面**：上方 Pipeline API（`/chat` `/gate` `/jobs/*`）vs 下方 `/run` `/approve`。  
3. **修代码落点**（工程）：  
   - 会话/游标：`lab-chat-session` / `pipeline-cursor` / `pipeline-chat`  
   - 门与 job：`pipeline-jobs` + `app/api/ops/delivery-lab/...`  
   - 展示：`LabPipelinePanel` / `labPublicView`  
4. **修完用同一题干新建一条 lab 回归**（或重跑本轮），不要在半残 session 上叠补丁。

### 3.2 类型二：模型生成问题（内容/喂料不对）

症状像「能跑通，但胡说、串阶段、盘用错、合盘污染、交付鸡汤」。工具是好的——要改 **提示词 / 喂料白名单 / 闸门**，不是改 LAB 按钮。

#### 3.2.1 怎么用 Trace 定位（Stage1–3）

每轮回复后固定看右侧五块：

| 块 | 问自己 |
|----|--------|
| **user / 喂料** | 是否灌了本阶段不该有的块？（如 opening 灌了交付菜单、solo 灌了对方盘编造） |
| **system** | 是否串了别的阶段人格/任务？path 前缀是否与 `solo/dyad` 一致？ |
| **reasoning** | 是否在算不该算的（理解阶段就算主辅）？ |
| **输出 / parsed** | 用户可见是否违规（恐吓、三人合盘、提前交付）？ |
| **meta** | 模型、tokens、耗时是否异常（空生成、截断）？ |

**判责口诀：**

- Trace 里 **喂料就脏** → 先修组装喂料 / `pageFeedFlags` / path pack，**别先骂模型**。  
- 喂料干净但输出仍脏 → 修该阶段 duty 提示词 + 必要时加闸。  
- 只有某一 path（solo/dyad）坏 → 查 `pivot-path-*` / dyad matrix 注入，不要改另一 path。

#### 3.2.2 常见内容问题 → 修哪里

| 现象 | 更像什么 | 优先改 |
|------|----------|--------|
| 未问清期望就宣称「够了」进 Stage2 | 理解门过松 | opening 提示 + 理解完整度逻辑；LAB 上点补充再确认验证 |
| 非二元题弹出收对方盘 | 二元误触发 | `dyad-compat` 检测 / 模型 `dyad_specific_other`；对照用例 A |
| 跳过对方盘后仍写「对方八字如何」 | 路径污染 | 确认 path=`solo` 且喂料无 partner；查 Stage2/交付 dyad 块是否误开 |
| dyad 却完全不提关系结构 | 喂料缺失或 path 未锁 dyad | 确认 collect 成功、matrix/summary 进 Call A feed |
| Call A 直接定主辅路径 | 阶段职责串 | Segment2 Call A 提示；用户可见应是多维观察 |
| Call B 议程像闲聊清单、倒逼不了交付 | Call B 提示/骨架 | agenda bridge 提示与 frame 对齐 |
| 收集阶段复读、不接芯片 | collecting 提示 / catch 逻辑 | collecting-v6 + 芯片文案是否进 user |
| Synthesis 后主辅与期望无关 | 汇总喂料或 covered_agenda 空 | 看 seed 进 LabSource 的 agenda/期望；再查 synthesis 输入 |
| 交付某页串了别页菜单（如 P4 灌 P3 SOP） | **页级喂料污染** | `page-feed-policy` 白名单；对照人审手册 §2.1 |
| 交付批断像鸡汤、无本盘钉 | thesis/prealloc/judgment 喂料或闸 | 交付人审手册循环：记类别 → 改 duty/feed → 重跑本步 |
| 盘 A 的结论出现盘 B 用词 | 创建时贴错盘 / lab 串源 | 新建 lab，重新导入正确 `base_analysis`；查 session_id |

#### 3.2.3 喂料「不准 / 不干净 / 污染」的修复流程

```
1. 在出问题的那一轮打开 Call Trace
2. 复制 user 喂料里「不该出现」的段落（或缺失的段落）
3. 标注污染类型：
   - 错盘 / 错 path
   - 跨阶段（opening←交付、Call A←主辅）
   - 跨页（P3←P4 菜单等）
   - 聊天垃圾进了交付（用户原句当结构事实）
4. 改「组装点」而不是改模型随机性：
   - Stage1–3：oriental / path pack / segment2 prompt builder
   - 交付：page-feed-policy + 该步 build*Feed
5. 同一 Lab 或新建 Lab：重跑该轮 / 该步，对比新 trace 喂料是否变干净
6. 喂料干净后若输出仍坏 → 再改该步 system duty + 人审类别账本
```

**禁止：**

- 把本案用户原句写进正则当唯一拦法（见交付人审手册）。  
- 闸过但人眼不过仍点「本步通过」。  
- Stage1–3 内容差就去改交付闸「补救」——应回上游重跑。

## 4. 推荐第一次测试日程（半日版）

| 时段 | 做什么 |
|------|--------|
| 0:00–0:20 | 登录、导入一张盘、创建全流程 Lab、熟悉左右栏 |
| 0:20–1:00 | 跑 **用例 A（solo）** 走完 1–3 → 看解锁 → 交付跑通 bootstrap→thesis（不必当天跑完六页） |
| 1:00–1:40 | 跑 **用例 C（二元跳过）**，核对 path=solo、无编造对方盘 |
| 1:40–2:20 | 跑 **用例 B（粘贴对方盘）** 或至少完成 collect + 确认后 Call A 喂料含合盘摘要 |
| 2:20–2:40 | 快速点 **D 或 E** 看边界行为 |
| 2:40–3:00 | 整理：LAB bug 列表 vs 模型/喂料类别列表；分别开修 |

## 5. 和「交付-only Lab」怎么选

| 你的目标 | 选 |
|----------|----|
| 已有 breakthrough_core / agenda，只抠八页与 Companion | **交付-only** |
| 要从提问→理解门→Call A/B→收集→汇总再进交付，并看 1–3 全量 trace | **全流程测试** |

全流程测交付质量时：仍用交付人审手册；不要因为 1–3「聊得通」就放松八页 Approve。

## 6. 一页速查

1. **设计题**：单楔 + 处境 + 期望；跑齐 A/B/C（+D/E）。  
2. **创建**：全流程模式 → 填出生信息 → 创建 Lab。  
3. **1–3**：聊 → 看 trace → 重跑或继续 → 门确认 → 等 job → Synthesis → 解锁。  
4. **交付**：Run → 审 → Approve；不过不放行。  
5. **坏了分两类**：页面/接口 → 复现 + 修 Lab API/UI；内容/喂料 → Trace 定责 + 改 feed/duty/闸。
