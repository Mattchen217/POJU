POJU 交付报告核心架构说明（v3 · 正文/依据分离修正版）
这版不是又一次臆测重写。核心内容是从你给的两份真实 Lab trace 反推出来的一个具体 bug,已经追到精确到行号的代码位置,并且用 p3-science-action.ts 自己的注释(它早就写对了)反过来验证。这份文档的目的,就是你说的——作为开发依据,不能再乱改。

一、最重要的一条原则,所有人必须先对齐这条
正文 ≠ 依据的白话翻译。这是两种不同性质的内容,不是同一份内容的两种呈现方式。

依据(命理批断):解释"为什么"。是命理推算出来的机制链,证明这条结论/策略只对这个人的盘成立,换个人换个盘就不一样。依据的存在,是为了给正文的可信度背书,不是依据本身要展示给用户看的核心价值。
正文:解释"是什么/怎么办"。是用户真正要读、要用的内容——对 P3 来说就是"可执行的策略和行动方案",不是命理机制的翻译版。
正文和依据的关系是"结论 + 论证",不是"原文 + 译文"。 删掉依据,正文应该垮(因为失去了"为什么只对你成立"的支撑),但正文的内容本身不能等于把依据里的命理术语换成白话——那样删完依据后,剩下的还是命理机制描述,只是换了个说法,并没有真正的策略内容。

你给的 trace 里,P3 的 strategy 字段写的是:"当前人生阶段与今年形成了一种合力,让原本就偏旺的火势进一步加强...需要借助你的输出表达来生助它"——这整段话删掉"人生阶段""火势""输出表达"这些换皮词,换回原本的"大运""忌神""食神",就是一段纯批断。这不是正文,这是依据穿了件马甲。 真正的 P3 正文应该是类似"建议你先争取 3 个月兼职试运行期,并在开口谈之前先把股权/话语权这两点问清楚,因为你的结构显示[某条依据]"这样的内容——前半句是真策略,后半句才挂回依据。

二、逐页"正文该是什么" vs "依据该是什么"
这条原则在每一页的具体表现不一样,不能一刀切。P2 例外,下面会解释为什么。

页	正文应该是	依据应该是	正文 = 依据翻译，可以吗
P1 直答	结论+主辅路径+一句为什么	（不显示，内部仍需锚点支撑，见上版文档第0节已确认）	不适用（本页不挂依据层）
P2 归因	本来就是解释性质——现象+机制，让用户明白"为什么会卡在这"	同一条批断（P2 本身就是把批断讲透，正文≈依据的可读版是这一页的正确设计）	可以，且本来就该如此（见下方说明）
P3 破局策略	可执行的策略+手段（怎么谈兼职、怎么问股权、精力怎么分配……）	支撑这套策略只对你成立的命理机制	不可以——这正是当前的 bug
P4 自我调频	可实操的东方策略+手段（非物化）	护城河维（timing/polarity/archetype）机制	不可以，同 P3
P5 风险预警	具体的坑+怎么防（指回 P3/P4 的哪条动作）	忌神/盲区/负向多维支撑	不可以，同 P3
P6 出门收尾	今晚一件事+近7日清单+带走三样	正向信号支撑	不可以，同 P3
为什么 P2 是例外：P2 的产品定位（report-blueprint.ts:64-65）本来就是"用命理讲透你为什么会卡住"——它的任务性质就是解释，不是给行动方案（p2-foundation.ts 的 FINALIZE_DUTY 原话："禁执行清单"）。所以 P2 的 surface/essence = 批断的白话版，这本身就是对的设计，不是偷懒。P3–P6 不一样，它们的任务性质是"给行动"，批断只能是行动背后的论证，不能是行动本身。

三、正确的三段生成管线（以 P3 自己的代码注释为范本）
这套设计其实已经在代码里写清楚了，只是没有被正确执行。p3-science-action.ts:104-129 的 buildAssignDuty 函数头部注释：

"Fact-pack assign (step 1) — structure claims only. Fill carries strategy/means; do not put life-action prose into unit_claim."

三段分工原文（p3-science-action.ts:107-112）：

"本页最终交付什么：科学主辅各 3 维：strategy + means（可动手的执行行动力）。那是 fill 的事。 本步（派工）只做什么：...写一句本盘结构主张...下一步专写...命理批断；再下一步 fill 才把批断译成 strategy/means。"

也就是：

assign：锁 unit_claim = 纯结构主张（"用神水制火"这类），calc_cite = 事实档摘录。明确禁止在这一步写生活化内容（p3-science-action.ts:126-129"禁止写进 unit_claim（留给 fill 的 means/strategy）"，清单里点名列了"兼职/全职/股权/律师协议"）。
深度依据 write：把 unit_claim 展开成完整 professional_evidence（≥两句机制链），仍然纯批断，不碰白话正文。
fill（正常模式）：把批断 + 本页候选菜单（P3 是 science_means_feed，来自"【P3 科学手段候选菜单】"）一起长成 strategy/means——这才是真正的正文生成步骤，p3-science-action.ts:74-93 明确要求"每条 means 须能回溯菜单中的帧/action_plan/收集事实"，"读完能动手，不是励志清单"。
这套三段分工本身没有问题，问题出在第 3 步没有正常运行。

四、发现的具体 bug：P3（及部分影响 P2）被锁死在错误分支
根因：fill-call.ts:96-101

const plainJudgment =
  fill_mode === "compress" &&
  deepPlan != null &&
  deepPlan.units.length > 0 &&
  deepPlan.units.every((u) => (u.chart_anchors?.length ?? 0) === 0);
这行代码的原始用意应该是一个兜底保护：如果深度依据那一步没能锁上任何 chart_anchors，就自动降级成"只翻译批断、不敢编策略"的保守模式，防止在没有命理支撑的情况下瞎编。

但现在 deep-evidence-write.ts 的设计永远把这个 plan 对象自己的 chart_anchors 字段留空（"chart_anchors 留空"这句指令在它的纠错文案里反复出现，deep-evidence-write.ts:137/205/427）——因为锚点已经改成在更早的 assign 阶段锁定（assign-binding-seed.ts:132），不再是 write 这步该填的字段。

结果：deepPlan.units.every(chart_anchors.length===0) 这个判断条件现在对每一次调用都成立，plainJudgment 永远是 true。这不是"新设计的第一步"，是一个原本用来防御边缘情况的兜底检查，因为一次架构调整（锚点搬家到 assign 阶段）而变成了永久误触发的开关。

连锁后果：fill-prompt.ts:139-140 的 judgmentTranslateOnly = plainJudgment && (key === "foundation" || key === "science_action") 因此对 P2/P3 永远为真，fill 因此永远走"只译批断"分支（fill-prompt.ts:148-159），这条分支明确禁止把候选菜单（science_means_feed）和处境内容喂进去（fill-prompt.ts:203-211 的 !judgmentTranslateOnly 判断把它们排除在外），也明确禁止"谈判建议""职场教练执行案"（p3-science-action.ts:41）。P3 该有的真实策略内容，从来没有机会被生成。

影响范围：

P3（science_action）：严重命中，因为它的正常模式和降级模式在内容性质上完全不同（策略 vs 翻译）。
P2（foundation）：命中但影响很小，因为 P2 的正常模式本来设计上就是"批断的白话版"（见第二节），降级模式和正常模式内容性质接近，问题不明显。
P4/P5/P6：不受这个特定条件影响——judgmentTranslateOnly 的判断只对 key === "foundation" || key === "science_action" 生效，其余页面走的是另一条不含此判断的 isCompress 分支。我没有针对 P4–P6 做同等深度的排查，不能保证它们没有其他独立问题，但至少可以排除这一个。
建议修复方向（两选一，需要你确认哪个是你要的）：

如果"只译批断"模式本来就该是一个诊断/QA 关卡（单独验证批断翻译保真度，不该替代正式产出正文的 fill 调用）——那么应该把这个判断从生产链路里去掉或者接到一个独立的 QA 调用上，生产链路的 fill 应该固定走正常分支。你给我看的两份 trace 界面标着"Lab"（对应 lab/run-step.ts），看起来本来就是一个分步调试台，不是正式交付链路——值得确认一下这两份 trace 是不是从 Lab 界面跑出来的，如果是，说明正式交付链路可能根本没被这个 bug 影响，只是 Lab 测试台本身在验证"只译批断"这一步时给你看到了这个中间产物，你误以为这就是最终正文。
如果这个兜底判断本来就该继续存在（防止 deep-evidence 没锁上锚点时瞎编）——那需要把判断条件改成检查真正相关的信号（比如 assign 阶段是否成功锁了 unit_claim），而不是检查 write 阶段这个现在永远为空的字段。
第 1 种可能性更大,因为 p3-science-action.ts 自己的注释把三段分工写得清清楚楚,没有任何地方提到"只译批断"应该是最终交付形态。我建议你先确认一下这两份 trace 到底是从 Lab 调试台跑出来的,还是从真正的 final-delivery 生产链路跑出来的——这个问题的答案决定了这是"生产环境的真实 bug"还是"调试工具的一个中间步骤被误读"。

五、按这条原则重新写的 P3 验收标准
在原有验收标准基础上,新增这一条,而且优先级最高:

☐ 正文必须包含依据里没有的东西：strategy/means 字段里必须能看到用户真实处境的具体元素（本案例应出现"兼职试运行""股权/话语权确认""开口谈判方式"这类具体内容），不能通篇只是命理机制的白话转述。自检方法：把 strategy 里所有描述"合力""调节力""输出表达""过载"这类结构隐喻词整句删掉，剩下的内容如果是空的或者只剩"因此需要平衡"这种空话，判定不合格。
☐ means 必须能回溯到候选菜单（means_candidate_ref 字段非空且能在 science_means_feed 里找到对应条目），而不是回溯到 evidence 本身。
☐ 依据（evidence/professional_evidence）本身的验收标准不变（第二版文档已有的深度/事实一致性硬闸），依据可以、也应该保持纯命理语言，不要求依据也讲人话——依据讲人话是第五节"合规翻译"那一步的事，不是本节讨论的问题。
六、这跟你说的"分 2 步走"是什么关系
你之前说的"第一步生成正文+依据里的命理批断，第二步做合规翻译"，方向完全正确，而且合规翻译那一步（mark-evidence-prompt.ts）本来就已经是独立步骤，不需要重新设计。

真正缺的、也是这次发现的问题所在，是**"正文"这一步本身被悄悄替换成了"依据的翻译"，而不是"依据支撑的策略"**。这不是"两步走"和"三步走"的区别，是"正文"这个词在实现里被理解错了。把第四节的 bug 修掉（让 fill 正常走 science_means_feed 那条分支），你原本设想的两步走设计——先出内容（正文+依据）、再合规翻译——就是成立的，不需要再引入新的架构层。
