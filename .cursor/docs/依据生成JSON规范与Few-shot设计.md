# 依据生成 JSON 规范与 Few-shot 设计

**目的**：把"一段依据需要几个命理真词"，从生成指令里写死的固定数字（当前是"3"），改成模型在生成 JSON 阶段自己论证并自检的判断过程。数字是结果，不应是指令本身。

**适用阶段**：`deep_assign` → `deep_write_evidence` 之间的中间产物（当前 assign 阶段输出的信号绑定结构），本文档定义这一层 JSON 应该长什么样、模型该怎么判断信号取舍、下游该验什么。

**关联**：命盘结构出处与 `dimension_id` + `inference_zh` 契约见 [命盘总纲与依据渲染规范.md](./命盘总纲与依据渲染规范.md)。

---

## 一、现状问题回顾

- 当前逻辑大致是：每段依据目标绑定3个 `⟦w:⟧` 真词，模型经常写丢到2个甚至1个，触发 `mark_slots_dropped` 重试；
- 全局 `validatePrimaryReuseCap`（同一真词全书复用≤2）可能在候选词撞上限时被直接剔除，且缺少替补逻辑，导致段落最终只剩1个词；
- 数量目标和逻辑有效性被混在一起：3个词不代表证据链完整，1个词也不代表证据链单薄——真正决定证据链是否成立的是"信号是否各自解释了结论里不同的部分，且缺一不可"。

---

## 二、JSON Schema 定义

```json
{
  "claim_id": "string，唯一标识，如 'financial_buffer_fragility'",
  "claim_zh": "string，该段依据要支撑的中文结论，用户最终会读到的表象/本质对应的那句话",
  "necessary_signals": [
    {
      "slug": "string, closed-set term; chart_primary_slug alias ok",
      "dimension_id": "optional thesis dimension id (requires inference_zh)",
      "inference_zh": "optional claim-specific inference (no paste conclusion_zh)",
      "role": "string, distinct explanatory role",
      "why_needed": "string, removal-test gap if missing"
    }
  ],
  "removal_test": {
    "passed": "boolean，模型对每个信号做完'去掉会怎样'的自检后，是否所有信号都是必要且不冗余的",
    "notes": "string，如果 passed=false，写清楚哪个信号被判定为冗余或哪里仍有缺口，交给重试环节处理"
  },
  "signal_count_rationale": "string，一句话说明为什么是这个数量（1个/2个/3个），不是因为凑数，而是这个具体结论本身需要几个独立维度"
}
```

### 字段说明

| 字段 | 作用 | 常见错误 |
|---|---|---|
| `role` | 强制模型说清楚每个信号"具体解释了什么"，而不是笼统地都在讲"能量不够" | 多个信号的 role 描述雷同或可互换，说明其实是同一个论证换了个词 |
| `why_needed` | 强制做"去掉测试"的书面记录，不是靠模型口头说"必要"就算数 | 写成"这个信号很重要"这种空话，没有具体指出缺了它论证断在哪 |
| `removal_test.passed` | 结构化的自检结果，下游可以直接拿这个字段做硬性拦截 | 模型选择性忽略自检，直接填 true |
| `signal_count_rationale` | 把"要几个信号"这件事的决策权交还给内容本身 | 沿用旧习惯，默认写"3"而不做实际论证 |

## 三、Few-shot 示例（正例 + 反例对照）

### 反例 A：信号不足，结论悬空

```json
{
  "claim_id": "safety_buffer_12mo",
  "claim_zh": "为什么必须先把安全垫攒够12个月",
  "necessary_signals": [
    {
      "slug": "锚元",
      "role": "解释当前能量不稳",
      "why_needed": "这个信号很重要"
    }
  ],
  "removal_test": { "passed": true, "notes": "" },
  "signal_count_rationale": "1个就够"
}
```

**问题标注**：`role` 写的是"能量不稳"，太笼统，无法解释"为什么具体是12个月这个数字"，也没有信号能解释"为什么是现在这个时间点要做这件事"。`why_needed` 是空话，没有指出具体缺口。这段论证实际上悬空——读者读完依据，仍然不知道"12个月"这个具体数字是怎么来的。**应打回重新 assign，补一个能解释"时间窗口紧迫性"的信号。**

### 反例 B：信号过多，存在冗余

```json
{
  "claim_id": "internal_transfer_option",
  "claim_zh": "为什么可以借内部平台资源做侧翼转型",
  "necessary_signals": [
    { "slug": "竞合", "role": "解释资源博弈心态", "why_needed": "..." },
    { "slug": "框架", "role": "解释与组织规则的绑定", "why_needed": "..." },
    { "slug": "登峰", "role": "解释能量的顶点状态", "why_needed": "..." },
    { "slug": "聚势", "role": "解释外部势头的汇聚", "why_needed": "..." }
  ],
  "removal_test": { "passed": true, "notes": "" },
  "signal_count_rationale": "4个信号全面覆盖"
}
```

**问题标注**：`removal_test.passed` 被草率标记为 true，但实际做去掉测试会发现——去掉"登峰"或"聚势"任意一个，结论依然可以从"框架"（组织绑定）单独推出，说明这两个是冗余的、可以互相替代的候选，不是各自解释了结论的不同部分。**这是"为了显得全面而硬凑"的典型情况，应该打回重新做 removal test，精简到2个真正互补的信号。**

### 正例：最小必要且充分的组合

```json
{
  "claim_id": "financial_buffer_fragility",
  "claim_zh": "财务安全垫的脆弱感",
  "necessary_signals": [
    {
      "slug": "竞合",
      "role": "解释'为什么积蓄总是攒不厚'——资源在同辈关系中被持续分流",
      "why_needed": "去掉此信号，无法解释为什么明明收入不低、缓冲却总显得单薄，其余信号无法单独覆盖这个具体现象"
    },
    {
      "slug": "岁环",
      "role": "解释'为什么是现在这个时间点感到紧迫'——当前时间气候放大了对安全垫厚度的敏感度",
      "why_needed": "去掉此信号，结论会显得是一个长期存在但不紧迫的问题，无法解释用户此刻主动求助的迫切性"
    }
  ],
  "removal_test": {
    "passed": true,
    "notes": "两个信号分别解释了'为什么攒不厚'和'为什么现在觉得紧迫'，去掉任意一个都会出现对应的解释缺口，无冗余"
  },
  "signal_count_rationale": "2个——一个解释现象成因，一个解释时间紧迫性，二者不可互相替代，也没有第三个维度需要补充"
}
```

**为什么这是好例子**：两个信号的 `role` 明确指向结论里不同的部分（成因 vs 时机），`why_needed` 具体写出了缺失哪一环会出现什么解释空缺，`removal_test.notes` 是可核查的论证而不是一句"通过"。数量是2个，不是因为凑数或抠数字，而是这个具体结论恰好需要且只需要两个维度。

## 四、下游验证规则（quality gate 需要改的地方）

现有 gate 大概率在数"marked_terms 数量是否等于3"，这个逻辑应该退休，替换为以下检查：

1. **`removal_test.passed` 必须为 true 才能进入 write 阶段**；为 false 的直接打回 assign 重试，不进入下游。
2. **`role` 去重检查**：同一段落内任意两个信号的 `role` 文本，做语义相似度检查（不是简单字符串比对），过高则视为冗余，打回重新做 removal test。**这条规则同时能防住"流展在P3和P4几乎写了同一段role"这类跨页面复制的情况**——如果两个页面各自的 assign 阶段都对同一个 role 描述做检查，能提前拦下重复。
3. **全局复用上限（`validatePrimaryReuseCap`）仍然保留**，但检查对象只针对 `slug`，且当某个候选 `slug` 因超限被剔除时，**必须触发替补逻辑**：从未超限的候选池中，按语义相关度重新挑一个能填补同一个 `role` 空缺的信号，而不是直接删除后留空——这是解决"上一轮很多段落莫名降到1个词"的关键修复点，建议单独排查现有代码是否只做了删除、没做替补。
4. **`signal_count_rationale` 抽查**：不强制要求特定数量，但如果发现连续多个段落的数量都稳定卡在1，且 `rationale` 写法高度模板化（比如反复出现"1个就够"），应该人工抽查这些段落是否真的只需要1个信号，还是生成时偷懒。

## 五、例外情况：某个结论确实需要4个以上信号怎么办

这种情况应该很少出现。如果频繁触发，大概率不是"这段论证真的需要这么复杂"，而是 `claim_zh` 本身粒度太粗，把几个应该分开的结论捏在了一起。

**处理方式**：优先尝试把这个 `claim` 拆分成两个粒度更细的子 claim，各自配一组更小的必要信号集合，而不是允许单个 claim 无限堆叠信号。只有在明确无法拆分（比如结论本身就是"多重因素同时作用产生的一个不可分割的现象"）时，才允许突破常规数量，且这种例外应该被标记出来，纳入人工抽查名单，防止变成新的"凑数"借口。

## 六、上线前验收清单

- [ ] 抽取10份历史报告，用新 schema 重新跑 assign 阶段，人工检查 `removal_test.notes` 是否言之有物，不是套话
- [ ] 检查是否存在两个不同 claim 的 `role` 描述高度相似（跨段落去重检查，针对"流展类"复制问题）
- [ ] 检查全局复用上限触发时，是否有替补信号补位，而不是留空导致该段降到更少信号
- [ ] 统计新版本中"单段仅1个信号"的占比，与旧版本对比，确认不是被动降级而是主动判断的结果
- [ ] 抽查是否有 claim 因粒度过粗触发4个以上信号，评估是否应该拆分

## 七、与既有方案的关系

- **不否定**此前落地计划里 A 项（跨页 prior 频次表 + 全局复用上限）的既有基础设施，本方案是在其之上，把"单段该配几个信号"这一层的决策逻辑，从固定数字改为内容驱动的判断；
- **需要重点排查**A 项里 `validatePrimaryReuseCap` 触发时的降级行为，这是本文档第四节第3条指出的关键修复点，怀疑是"术语数量不增反减"的直接原因；
- Locale 泄漏（`锚元water`、`耗元fire`）和未解析占位符（`【气候交织】`）问题不在本文档范围内，仍按此前 D 项方案单独修复，不依赖本次 schema 调整。
