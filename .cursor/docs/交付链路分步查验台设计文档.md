# 交付链路分步查验台设计文档

**目的**：现状是整条依据生成链路（总纲→assign→write→mark→polish→组装）是黑盒的，只能看最终成品，出问题（如L383）只能靠倒推。本方案在**现有生成代码的每个阶段边界加"存快照"的钩子**（不新建执行路径，链路照常跑），再建一个**完全独立、内部专用的只读调试页面**去读这些快照，按"页面→阶段→尝试次数"逐层展开，每个阶段一个按钮，点开看这一步模型收到了什么、吐出了什么、gate判了什么。

---

## 一、总体架构

```mermaid
flowchart LR
  subgraph 正式生成链路（不改执行逻辑，只加钩子）
    thesis[总纲生成] --> assign[assign] --> write[write] --> mark[mark/polish] --> gate[质量闸] --> book[组装入库]
  end
  thesis -.存快照.-> store[(快照存储\n挂在job_id下)]
  assign -.存快照.-> store
  write -.存快照.-> store
  mark -.存快照.-> store
  gate -.存快照.-> store
  store --> debugpage[/internal/debug 独立只读页面/]
```

**两条硬性原则**：
1. 快照钩子只做"记录"，不做"拦截"或"等待"——链路该怎么跑还怎么跑，不会因为加了钩子而变慢或行为不同（钩子本身要异步写、失败不阻塞主流程）；
2. 调试页面是纯只读的观察窗，不提供"手动放行/跳过gate"之类的操作入口——如果调试时发现某一步gate判错了，回去改gate代码本身，不在调试页面里开后门，否则调试台和正式行为就会分裂成两套逻辑。

## 二、需要埋点的阶段清单（越细越好，覆盖每一次模型调用和每一次gate判定）

| stage_id | 阶段 | 对应现有函数/文件（沿用此前几份计划里出现的命名） | 要抓的输入 | 要抓的输出 |
|---|---|---|---|---|
| `thesis.gen` | 总纲单维度生成 | `build-chart-thesis.ts` / `ensure-job-chart-thesis.ts` | 真算给这个维度的原始结构化字段 | 该维度完整JSON（`classical_basis`各清单项、`conclusion_zh`、`wuxing_relations`） |
| `thesis.extend` | assign触发的总纲扩展 | `extendThesisDimension` | 触发扩展的claim + 缺失原因 | 扩展后的新增/修改字段 |
| `prealloc` | 全书primary预分配 | `ensureJobChartPrimaryPrealloc` | inventory候选池 | 各页预分配到的primary清单 |
| `assign` | 单个claim的信号绑定 | `deep-evidence-assign.ts` | 该页已用信号频次表(`prior_signal_roles`)+可引用的总纲维度 | 原始`necessary_signals`+`removal_test`+`signal_count_rationale` |
| `assign.gate` | assign结果校验 | 同上内部校验逻辑 | assign原始输出 | 通过/打回，命中的具体规则（`removal_test failed`/`inference_cross_dup`/`primary_reuse_cap_exceeded`等）+重试次数 |
| `write` | 依据正文生成 | `deep-evidence-write.ts` | assign通过后的信号绑定+总纲`conclusion_zh`/`wuxing_relations` | 原始依据文本（mark之前的样子） |
| `mark` | 术语打标 | `term-marking.ts` | write输出 | 带`⟦w:⟧`槽位的原始标记结果+槽位数 |
| `mark.gate` | 打标槽位校验 | 同上 | mark原始输出 | 通过/打回（如`mark_slots_dropped`/`mark_slots_lt2`）+ 每次reinject的具体改动 |
| `polish` | 白话润色+locale转换 | `polish-marked-evidence.ts` | mark输出 | 润色后文本（英文token本地化前后对照） |
| `encode` | 未解析词槽兜底 | 同上 / `bracketUnresolvedTerm`相关逻辑 | polish输出 | 最终encode结果，特别标注是否触发了未解析兜底 |
| `remnant.gate` | 落库前半渲染残骸扫描 | `evidence-remnant-gate.ts` | encode输出 | 通过/拦截，命中的具体残骸特征（裸`【】`/未闭合`⟦w:`/连接模板词重复） |
| `book.assemble` | 最终组装拼书 | `final-delivery-stage-runner.ts` | 各页最终通过的依据集合 | 拼装后的完整页面文本 |

每个stage都要能看到**是不是被重试过**，重试过的话每一次尝试都单独留一份记录，不能只留最后成功的那次——这是查L383这类问题的关键，因为很可能问题恰恰出在某次重试的repair逻辑里。

## 三、每条快照记录的字段结构

```json
{
  "job_id": "job_xxxx",
  "page_id": "P4",
  "claim_id": "energy_overload_conversion",
  "stage_id": "mark.gate",
  "attempt_number": 2,
  "timestamp": "2026-09-09T10:22:31Z",
  "duration_ms": 8421,
  "input_payload": { "...这一步实际吃进去的原始输入，包括prompt里注入的上下文..." },
  "raw_model_output": "...模型这一步的原始输出，不经任何后处理...",
  "processing_actions": [
    { "action": "reinject_missing_slot", "detail": "槽位3缺失，触发重新注入" }
  ],
  "gate_verdict": {
    "passed": false,
    "failed_rule": "mark_slots_lt2",
    "detail": "重试预算用尽仍不达标"
  },
  "output_to_next_stage": "...如果通过，传给下一阶段的最终内容..."
}
```

字段设计的关键点：`raw_model_output`必须是**未经任何后处理的原文**，`output_to_next_stage`是**经过这一步所有处理（repair/reinject/兜底）之后实际往下传的内容**——两者分开存，这样才能一眼看出"这一步模型自己写崩了"还是"模型写得还行，是后处理逻辑把它改坏了"，这正是L383目前查不出来的地方。

## 四、调试页面设计（`/internal/debug/job/{job_id}`）

### 4.1 入口：job选择

- 列出最近的delivery job（建议默认只展示标记为"内部测试"的job，如需查真实用户的job用于排查具体投诉，走单独的审批/审计流程，见第六节）；
- 每个job展示基础信息：用户标识（内部脱敏）、生成时间、当前状态（正常/有页面paused/有gate拦截记录）。

### 4.2 总览层：整书状态图

进入某个job后，先展示一张**整书状态图**（复用现有pipeline的mermaid风格），P1-P7每一页用颜色标出状态：
- 🟢 绿色：全程一次通过，无重试；
- 🟡 黄色：触发过重试但最终通过；
- 🔴 红色：某个gate拦截失败，或触发过paused。

点击某一页，展开这一页下面的所有claim列表，每个claim同样按上面的颜色标注状态，方便一眼定位到"到底是哪一页哪一条崩的"，不用从头翻到尾。

### 4.3 逐阶段查看：一个claim内，每个阶段一个按钮

这是你要的核心交互——点进某个claim后，界面按第二节的阶段清单，**从上到下排一列按钮**（总纲引用 / assign / write / mark / polish / encode / 残骸扫描 / 组装），每个按钮默认折叠，点开才展开这一步的详情，避免一次性堆太多信息看不过来。

每个展开的阶段面板，固定用**左右两栏**布局：
- 左栏：这一步的`input_payload`（这个阶段吃进去了什么）；
- 右栏：`raw_model_output`（模型原始吐出了什么）；
- 下方单独一条：`gate_verdict`（判定结果，失败的话高亮显示命中了哪条规则）；
- 如果这个阶段有多次尝试（attempt_number > 1），面板顶部给一个**尝试次数切换条**（tab或下拉），可以来回切换看第1次、第2次……每次尝试之间用**diff高亮**标出改动了什么，方便一眼看出repair逻辑到底改了哪里、改坏了没有。

### 4.4 辅助功能

- **原始JSON/渲染视图切换**：工程排查用原始JSON，非技术人员（比如你直接审内容质量）可以切换成排版过的可读视图；
- **筛选**：按`stage_id`筛选（比如只看所有mark.gate失败的记录）、按`failed_rule`筛选（比如只看所有`inference_cross_dup`触发的case），这样能快速做"这类问题在这个job里一共出现几次"这种统计；
- **导出**：支持把某个claim的完整分阶段trace导出成一份文本，方便你截图/贴给团队讨论，不用每次都截很多张图。

## 五、存储方案

- **不新建一套独立存储系统**，复用现有job状态持久化机制（此前落地计划里提到的"总纲挂在xhigh job state"、Wave A/B的ready状态追踪走的是同一层），新增的快照记录按`job_id + page_id + claim_id + stage_id + attempt_number`这个组合key挂在同一存储层下面，逻辑上是"job状态"的一个扩展分支，不是平行的新系统；
- 快照写入必须是**异步、失败不影响主流程**——如果存快照这个动作本身出错，最多导致这一条调试记录缺失，绝不能让正式的报告生成因此报错或变慢。

## 六、权限隔离与隐私（这一条不能省，直接对应项目本身"用户数据本地化隐私"的红线）

调试页面会展示用户**真实的命理真算数据和生成过程中的中间产物**，这是敏感个人数据，需要单独的隔离设计：

1. **独立路由、独立鉴权**：`/internal/debug/*`不能复用面向付费用户的登录态/session机制，必须走单独的内部账号体系（比如公司邮箱SSO或IP白名单），且这部分路由代码**不能被打包进用户端产品的前端bundle**，避免被扒包发现调试接口；
2. **默认只对"内部测试job"开放**：日常调试优先用内部生成的测试账号数据，不需要动辄查真实用户数据；
3. **查看真实用户job需要审计留痕**：如果确实需要排查某个真实用户的投诉/异常case，查看行为本身要记日志（谁在什么时间查看了哪个job），不能无痕访问；
4. **快照数据要有留存期限**：不能无限期攒着——建议默认30-90天自动清理，或者只在job被明确标记"需要人工复核"时才保留快照，其余job默认不产生持久化快照（见第七节的采样策略），避免变成一份没人管理、游离在正式用户数据保护范围之外的敏感数据副本。

---

## 七、上线策略：默认关闭，按需/采样开启，不是给100%生产流量都开销

给每个job的生成过程都存这么详细的快照，在生产环境全量开启会有明显的存储和性能成本。建议：

- **阶段一**：先给内部测试账号生成的job，默认开启全量快照，用于当前这一轮质量排查和迭代；
- **阶段二**：正式用户流量，默认不开快照，但支持**按job单独打开"trace模式"**（比如生成时带一个内部flag，或者事后如果某个job触发了红色gate失败/paused，自动补开快照留存，方便復盘），不需要无差别记录所有生产流量；
- **阶段三（可选，暂不做）**：如果调试台用顺手了，后续可以考虑加一个"沙盒重跑单个阶段"的功能——比如只重新跑一次某个claim的write阶段，用来快速验证改完prompt后是不是真的好了，但这个功能要明确标注成"沙盒重跑，不写回正式job"，避免和第一节"不新建执行路径"这条原则冲突，这次先不做，等基础的查看功能稳定之后再考虑。

## 八、验收标准

- [ ] 用一个已知有问题的历史job（比如产出过L383的那次），跑通整个调试页面，能清楚看到：mark阶段第几次重试引入了残留的连接模板词、encode阶段是不是正确处理了未解析槽；
- [ ] 确认调试页面不出现在任何用户可访问的路由/导航里，且未被打包进面向用户的前端产物；
- [ ] 确认快照写入失败时，不影响正式生成链路的成功率和延迟；
- [ ] 确认查看真实用户job时，有审计日志留痕；
- [ ] 确认快照数据有明确的留存期限和清理机制。
