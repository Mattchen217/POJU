## 〇、总体判断（定调,先读这段）

三个月没跑通,不是架构方向错了,是几个**具体的、已经定位到行号的 bug**,不是"重新设计"能解决的问题,是"改对几处代码"能解决的问题。这轮排查确认的核心工程资产是扎实的:

- 真实排盘计算引擎(`chart-fact-pack.ts` 用 `computeDayunRelations`/`computeLiunianRelations`/`computeNatalChartRelations` 等函数算出结构化事实,不是让模型自己现算)

## 一、优先级 P0：把交付报告本身做扎实

### 1.1 六页定位——已确认正确,不需要调整

| 页 | 定位 | 正文该有什么 |
|---|---|---|
| P1 直答 | 结论 + 1主1辅方案 + 一句为什么 | 结论本身,不挂依据层 |
| P2 归因 | 为什么会卡在这困境里 | **例外**:正文=批断的白话版,这是对的设计（见1.2节说明为什么P2例外） |
| P3 科学策略 | P1 主辅方案的可执行策略+行动 | 必须是真实策略（谈判方式、资源分配等），不能是命理机制翻译 |
| P4 东方调频 | P1 主辅方案的东方自我调频 | 同 P3，护城河维优先，反物化 |
| P5 风险预警 | 执行 P3/P4 时要注意的坑 | 每条能指回具体是执行哪条动作时会栽 |
| P6 出门收尾 | 今晚一件事+近7日清单+身份收尾 | 摘自 P3/P4 已有内容，不独立新编 |
| 附录 | 结构数据存档 | 装配时合并，非独立生成任务 |

### 1.2 核心原则：正文 ≠ 依据的翻译（所有后续开发必须先对齐这条）

- **依据（命理批断）**：解释"为什么"，证明这套结论/策略只对这个人的盘成立。
- **正文**：解释"是什么/怎么办"，是用户真正要用的内容。
- **P2 是唯一例外**：P2 的产品任务本身就是"讲透归因"，所以它的正文=批断白话版是对的设计。**P3/P4/P5/P6 的正文绝不能是批断翻译**，必须是真实可执行内容，只是要能被依据支撑。

自检方法：把正文里"合力""调节力""输出表达""过载"这类结构隐喻词整句删掉，剩下的如果是空的或者只剩"因此需要平衡"这种空话，判定不合格。

### 1.3 Bug #1（最严重）：P2/P3 的 fill 被永久锁死在"只译批断"降级分支

**根因**：`lib/llm/pro/delivery/page-schema/fill-call.ts:96-101`

```ts
const plainJudgment =
  fill_mode === "compress" &&
  deepPlan != null &&
  deepPlan.units.length > 0 &&
  deepPlan.units.every((u) => (u.chart_anchors?.length ?? 0) === 0);
```

这个判断本意应是兜底保护（深度依据没锁上锚点时降级），但 `deep-evidence-write.ts` 现在设计上**永远**把这个 plan 对象自己的 `chart_anchors` 字段留空（锚点已改为在更早的 assign 阶段锁定，`assign-binding-seed.ts:132`）。结果这个条件**对每次调用都恒为真**，`plainJudgment` 永远是 `true`。

**连锁后果**：`fill-prompt.ts:139-140` 的 `judgmentTranslateOnly` 对 `foundation`/`science_action` 永远触发，fill 永远走"只译批断"分支（`:148-159`），这个分支明确禁止喂入候选菜单（`science_means_feed`）和处境内容（`:203-211` 的 `!judgmentTranslateOnly` 判断把它们排除在外），也明确禁止"谈判建议""职场教练执行案"（`p3-science-action.ts:41`）。**这就是为什么真实 Lab trace 里 P3 的策略正文只字未提用户案例中的兼职/股权问题——不是模型没写好，是这条分支从设计上就不许它写。**

`p3-science-action.ts:100-129` 自己的注释早就写清楚了正确设计：assign 只锁结构主张，深度依据只写纯批断，**fill 正常模式才该把批断+候选菜单一起长成 strategy/means**——现在这条正常模式因为上面这个 bug，从来没机会跑。

**验证优先**：先确认之前给我看的那两份 trace，是从 Delivery Lab 调试台跑出来的，还是从真正的 `final-delivery` 生产链路跑出来的——这决定了这是"生产环境实际在发生的 bug"还是"调试工具的中间步骤被误读"。

**修复方向（二选一）**：
1. 如果"只译批断"该是独立诊断关卡，不该替代正式 fill——去掉这个自动触发条件在生产链路里的作用，生产的 fill 固定走正常分支（读 `science_means_feed`）。
2. 如果这个兜底该继续存在——把判断条件换成检查真正相关的信号（比如 assign 阶段 `unit_claim` 是否成功锁定），而不是检查现在永远为空的 write 阶段 `chart_anchors` 字段。

**影响范围**：P3 严重命中（正常模式和降级模式内容性质完全不同）；P2 命中但影响很小（P2 正常模式本来就该是批断翻译，见1.2节）；P4/P5/P6 不受这条判断影响（`judgmentTranslateOnly` 只对 `key==="foundation"||"science_action"` 生效）。

### 1.4 Bug #2：`primary_backup_hint` 静默降级，P3/P4 可能跟 P1 最终内容不一致

**现状**（`lib/llm/pro/delivery/page-schema/upstream.ts:129-148`，作者自己写的依赖表）：

```
| Page | 是否需要 P1 的 page_schema | 数据源 |
| P2   | 不需要 | finalize + breakthrough_core |
| P3   | 不强制（优先读P1，读不到就退） | loadPrimaryBackupHint ∥ breakthrough_core |
| P4   | 不需要 | agent_v2 question + breakthrough_core |
| P5/P6| 硬性需要 P1+P3+P4 | ActionBrief 抽取器 + fuse feed |
```

真正的问题不是"顺序"（P1不需要排在P3/P4前面，产品设计上P1-P4本来就该并行跑，这样最快），是**一致性**：`breakthrough_core`（收集阶段/聊天环节就定下的早期初判）和 P1 自己最终生成的主辅方案（`loadPrimaryBackupHint` 读到的版本），如果 P1 的 finalize 被允许自由发挥而不是忠于 `breakthrough_core`，两者可能在实质内容上走岔——用了早期版本的 P3/P4，就可能跟最终呈现的 P1 对不上。**P4 目前的代码甚至从来没尝试读 P1，永远只用 `breakthrough_core`。**

**修复方向（已确定，不是可选项）**：P3/P4 必须真正读取 P1 生成的内容、锚定 P1 定下的 1 主 1 辅方案，不允许降级成不贴题的内容。具体改法：
1. 去掉 `loadPrimaryBackupHint`（`:129-138`）读不到就返回空字符串、让上层静默切 `breakthrough_core` 的做法——改成"P1 没好，这个任务就是 not ready，继续等"，不允许用旧数据顶替。
2. 在 `task-dag.ts` 里给 P3(`science_action`)、P4(`metaphysics_action`) 的 assign 任务加一条依赖边，依赖 `ready(direct_answer)`——跟现在 Wave B（P5/P6）等 P1+P3+P4 是同一种写法，只是多加两条边，让 P1 真正排在 P3/P4 前面执行，而不是并行后靠降级兜底。
3. **改之前先拉 P1 的真实平均耗时/失败率**——P1 跳过深度依据，理论上是六页里最快的一页，加这个依赖增加的等待时间应该很小，但这是架构推断，不是实测数据，需要确认后再动手，避免撞上 40 分钟任务墙。
4. P1 真失败了，交付任务该失败/重试，不该让 P3/P4 用旧数据将就跑完六页——**宁可交付慢一点或报错重试，也不能让 P3/P4 生成一份跟 P1 对不上的内容**。

**重要澄清（关于 Lab 页顺序和生产环境是否联动）**：这一条容易被误解，专门说清楚。查了 `lib/llm/pro/delivery/lab/run-step.ts` 的 import 列表，Lab 页调用的是跟生产环境**同一批底层执行函数**（`runPageSchemaFill`、`runDeepEvidenceWriteChunk`、`runDeepEvidenceAssignCall` 等），这部分是共用的——所以 1.3 节 Bug #1 那种"改函数内部逻辑"的修复，改一处，Lab 和生产会同时生效，不用两边分别改。**但 Lab 页的 30 步执行顺序，是 `run-step.ts` 里自己写死的一份顺序，完全没有引用 `task-dag.ts`/`upstream.ts` 里那套依赖关系声明**——也就是说 Lab 的顺序和生产环境的 DAG 调度，现在是两套完全独立、互不联动的东西，不是"一个是串行版一个是并行版"的关系，是"两个人各自写了一份顺序"的关系。这意味着：**上面这条 P3/P4 必须等 P1 的修复，只改 `task-dag.ts` 只会影响生产环境，不会让 Lab 页的步骤顺序跟着变**——如果希望 Lab 页调试时也能反映"P1 先于 P3/P4"这个真实依赖（这样调试时看到的顺序才是生产环境真正会发生的顺序），需要额外去改 `run-step.ts` 里那份写死的步骤列表，把 P1 挪到 P2 之后、P3 之前。这是两处独立的改动，缺一不会互相自动同步。

### 1.5 Bug #3（新发现，影响面比 Bug #1 更大）：锚点质量闸在 `sanitize.ts` 里被同一条恒真条件系统性禁用，不只影响 P4

**根因**：`lib/llm/pro/delivery/page-schema/sanitize.ts`（约1516-1522行，"P0-4·单元 chart_anchors 质量闸"）里，有一份跟 `fill-call.ts:96-101` **完全独立、逻辑完全相同**的 `plainJudgment` 计算：

```ts
const plan = opts?.deepEvidencePlan;
const plainJudgment =
  Boolean(plan?.units.length) &&
  plan!.units.every((u) => (u.chart_anchors?.length ?? 0) === 0);
...
allowEmptyAnchors: plainJudgment,
```

这个值传进 `assessUnitAnchorQuality`（`anchor-quality.ts:118-165`），当一页所有内容单元 `chart_anchors` 全空时：`allowEmptyAnchors` 为 `true` 就只记一条 note 放行（`structuralFail: false`），为 `false` 才会判 `structuralFail: true, reason: "all_content_units_missing_chart_anchors"` 打回重写。

因为这个条件现在对六页恒为真（跟 Bug #1 同一个原因：深度依据 write 阶段设计上永远留空锚），**"全空锚必须打回重写"这道安全网，对六页全部页面现在都是失效的**，不只是 P3/P4——是全部六页的 fill/compress 输出，只要模型某次漏了锚点，现在都不会被这道闸拦住。真实 trace 证实：P4 六个维度 `chart_anchors` 全空，gate 依然 `PASSED, attempts=1`。

**这条 Bug #1/#2 的修复方案（只改 `fill-call.ts`）覆盖不到**，必须单独修：把 `sanitize.ts` 这处 `allowEmptyAnchors` 的计算方式，改成跟 `fill-call.ts` 里 Bug #1 修好之后的判断**同源**（比如同样只对 `pageKey === "foundation"` 允许空锚），而不是各自独立重新猜一遍。另外 P4 的重试纠错文案（`fill-call.ts:324`）是六页里唯一没有写 `chart_anchors≥1` 要求的，建议一并补上。

### 1.6 P4 正文骨架：必须由 timing/polarity/archetype 撑起，不能是"自我调频语言包装的 P3 建议"

`p4-means-gate.ts` 已定义护城河维分级：**timing（时机）/polarity（旺衰/姿态）/archetype（结构角色）为主，rhythm（节奏）/mindset（心态）只能辅助、不能整页唯一支撑**。真实 trace 显示当前六个维度没有一个在做这三类主维——不是给不出真实计算的时间窗口/旺衰判断/结构角色定位，是写成了通用压力管理建议（少数）+ P3 风格谈判建议（多数），只是套了"能量系统""内在驱动力"这类语言外壳。

**验收自检需要加严一条**：不能只检查"删掉命理修辞词后是否还成立"（这份 trace 删了修辞词，剩下的"找律师、设定试水期、文档化产出"依然通顺——只是这是 P3 该给的）。真正该检查的是：**删掉具体的日期/旺衰判断这个"计算结果"之后，剩下的指令还成立吗？如果不管什么时机说都成立（"找人聊聊""保护收入""留好文档"），说明没有 timing/polarity/archetype 撑着，是 P3 内容换了外壳，判不合格。**

**内容形态不强制是"自我调频"，但必须满足**：(1) 每个维度必须能挂上真实计算出的锚点（具体流年/流月/大运关系，或具体十神/五行旺衰判断）；(2) 必须落到 timing（具体窗口）或 polarity（具体姿态判断）或 archetype（这个人在此类关系结构里的真实定位）三者之一，不能只是情绪/节奏类的辅助内容；(3) 内容必须是"只有这个人的盘才会得出"的，换一个人同样的处境，具体日期/判断依据应该不一样。

**长期方向（不在本轮，先记录）**：等 match（二人合盘）接入后，P4 是承载"两人结构关系"真算内容最自然的落点——谁在关系结构里天然话语权更重、两人时机窗口是否重叠、张力点具体在哪——这类内容比单人自我调频的护城河更深，是通用职场教练给不出来的东西。这条不影响本轮 P0 的执行范围，仅作为 P4 未来自然生长的方向记录。
### 1.7 P6 命名与可追溯性

- 当前 `PAGE_LABEL` 是"P6·行动建议(出门仪式)"（`p6-signals-close.ts:9`）——"行动建议"四个字跟 P3/P4 撞车，容易让人（包括未来的开发者）怀疑这一页是不是多余的。**建议改名**，换成贴合实际设计的名字（如"出门仪式"/"今晚就开始"），内部文档和 UI 标题一起改。

## 二、优先级 P1（P0 稳定后再做）：Match 并入收集阶段

- 不新增 Agent 框架，不用 JEV 做意图判断——直接在收集阶段加一个确认弹窗，明确问用户"这件事是否涉及另一个具体的人"，用户点"是"才触发第二人八字录入。UI 确认比任何分类模型都更可靠、更省事。
- 弹窗触发后：录入第二人生辰 → 跑合盘计算 → 结果作为额外 `chart_inputs` 喂进现有六页管线（比如 P2 的归因、P3/P4 的策略可以引用二人结构关系）。
- 不需要新建计算引擎之外的架构——这部分工作量主要在"合盘计算模块"+"收集阶段多一步 UI 确认"，不涉及 P0 阶段修的东西。

## 三、优先级 P2（P0+P1 之后）：30 天每日提醒，作为独立服务交付，不进报告

### 3.1 已经否决的两个形态,不要再考虑

- **并成第7/8页**：否决。"页"在现在的架构里意味着"生成一次、装订一次、封版"（assign→深度依据→fill→mark→assemble），30天提醒的内容依赖当天的日柱和进度，是"还没被计算出来"，不是"内容长"，本质上不该被"装订"。硬塞成一页，要么变成预生成30天内容一次性塞进报告（等于复活了已经被毙掉的"四周甘特表"，只是天数从28变成30），要么名实不符，未来会像 Bug #1 那样埋雷。
- **塞进 P6**：否决。P6 现在的设计是"一次性独立收尾，无回来追踪钩子"（这是退役独立 `thirty_day` 页时已经做过的取舍），30天陪伴需要"能被反复访问、每天刷新、接得住用户提问"，这和 P6"生成一次就完事"的本质矛盾。

### 3.2 采用的形态：报告 + 独立的30天陪伴服务，一次购买拿到两样东西

产品体验上是一个整体（一次购买），后端是两套独立跑法——报告走六页装订流程，30天陪伴走类似 atmos 现有的"每天重新算一次"的架构，只是内容源从"通用今日运势"换成"这份报告锁定的具体决策"。

### 3.3 内容定位：中间态（已确认，不是纯提醒，也不是完整反馈闭环）

- **不做纯提醒**（只锚定话题不锚定报告已有的具体内容）——这跟"换个话题的每日吉凶"没有本质区别，没有真正解决"读起来像算命"的问题。
- **不做完整执行反馈闭环**（追踪进度+收用户反馈+实时调整后续内容）——复杂度是另一个量级的东西（要处理用户断更、反馈内容合规检查等一堆边界情况），现阶段不做。
- **采用中间态**：报告生成时已经产出的 `action_brief`（P3策略、P4调频、P6近7日清单）本身不用重新生成，按30天做一次**确定性排期**（前7天对齐P6已排好的清单，后23天把P3/P4剩余手段按优先级摊开——这是代码逻辑，不需要模型）。每天推送的内容 = 排期里今天该看哪条现成清单（摘录，不重新编）+ 当天日柱跟这条行动的时机搭不搭（复用 atmos 现成的每日计算引擎，多喂一个"今天该关注哪条具体行动"的上下文）。**不问用户做没做，不根据反馈改后续内容**——排期在报告生成那一刻就已经能确定，需要每天现算的只有"日柱时机"这一小块。
- **"每日一问"完全独立于上面的按天推送逻辑**，不要互相牵连——用户随时可以基于报告内容+命理数据提问，回答不改变后续几天的排期。这是一个开放式、可能需要记住之前几天问过什么的对话式模块，跟 atmos 那种"单次生成一段话"的调用方式不是一回事，建议当独立模块设计。

### 3.5 进入这个阶段前需要先定的数据模型问题

- 陪伴周期怎么开始（报告生成完自动开启，还是用户手动确认开启）
- 每天的状态怎么存（生成过的内容存哪、用户问过的问题存哪）
- 30天结束后这份记录是保留给用户回看，还是清空
- （可选，留口子不强制现在做）给每天的行动项加一个 done/没做的勾选，先只存起来给用户自己看进度，不接入生成逻辑——为以后如果要做自适应版本留数据基础，但现在不需要为这个可能性先做复杂度
